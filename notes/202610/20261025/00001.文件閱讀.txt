  1. Quotation 先只管版本

  同意。來源、hash、核准與安全模型暫不納入本階段 Contract，只保留：

  • TargetName
  • System.Version
  • runtime value
  • exact/latest 選擇

  2. Pinning 規則

  我建議明文化成：

  建立 Agent incarnation
      argString 有版本  -> resolve Exact version 並 pin
      argString 無版本  -> resolve 當時最大版本並 pin

  Register(version, value)
      只更新 registry
      不改變既有 incarnation 已 pin 的 value

  重新建立 Agent incarnation
      重新 resolve

  因此相同版本 hot overwrite 後：

  • 現有 Agent 繼續使用舊 value。
  • 重起後，指定相同版本的 Agent 會取得新 value。
  • 未指定版本的 Agent 重起後取得當時最大版本。

  Register : Version * 'T -> unit

  3. 「在哪個節點 resolve」的意思

  靜態 VersionRegistry<'T> 只存在於目前 .NET process 的記憶體。

  例如：

  Process A：Wrapper actor + Registry A
  Process B：Native actor  + Registry B

  在 A 執行：

  Versioned<MyFun>("X").Register(...)

  不會自動讓 B 的 Registry 也出現該函數。

  所以我的意思只是：

  • 若函數由 Wrapper 執行，就在 Wrapper 所在 process resolve。
  • 若函數由 Native actor 執行，就必須在 Native 所在 process 已經註冊並 resolve。
  • 不要嘗試把 closure／compiled function 經由 IActorRef 傳到另一個 process。

  如果目前全部在同一 process，這點完全不構成問題；也不需要現在增加 distributed registry。

  4. Collect 與 DB

  你說得對：DB 一邊寫、一邊查沒有我先前描述的問題。

  我擔心的是目前這個型別：

  type WrappedReActDataFlow<'T> =
      ConcurrentQueue<ReActDataDirection * ReActDataStream<'T>>

  以及：

  Collect : unit -> Result<ConcurrentQueue<...>, exn>

  Agents
    ↓ messages
  ReActLoop / Message Hub
    ↓ internal write queue
  DB
    ↑ cursor/page query
  Collect
    ↑
  Wrapper / User

  也就是：

  • ConcurrentQueue 可以存在 implementation。
  • 只有 DB writer 消費 write queue。
  • Collect 從 DB 查詢，不碰 write queue。
  • Collect 回傳 immutable array/page，而不是可變 queue。
  • 新 prompt 和 Agent 回應可以持續並行寫入。
  • Wrapper 透過 cursor/watermark 反覆 Collect，再生成、再派送。

  • 一個 dispatch cycle 在目前 prompt watermark 已處理、所有已派出的 Native 都結束後完成。
