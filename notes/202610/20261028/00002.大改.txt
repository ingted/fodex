  ### 4. Explicit 與 implicit COT

  兩種觸發來源不同，但可以共用同一個 operation：

  Explicit：/wrapper_cot ...
  Implicit：wrapper regex 命中「那段 code」之類的指涉
      ↓
  InvokeWrapperCot（versioned FodexFun）
      ↓
  從 persisted ReActDataStream 做 bounded selection
      ↓
  AcquireParticipant
      ↓
  把整理後資料送給 COT participant
      ↓
  逐步 SteerTurn 給 main participant

  其中「最近 20K token＋regex」只是 v1.0.0 的 context-selection policy，未來可以換其他版本。

  我不建議查詢 RouteReActDataStream + sinked data 兩套來源。正確模型應該是：

  • RouteReActDataStream 成功後，事件已經 durable persisted。
  • MainWrapperToHuman 也屬於 persisted stream。
  • sink 只是 DB 資料投影到 user 的 side effect，不是第二份權威歷史。

  如此 COT 只查 persisted ReActDataStream。不用做 TencentDB memory，也不用讓 participant 理解 DB schema。

  所以你對高階 operation 的理解沒有根本錯誤；只是 operation 應包含整段 deterministic orchestration，而 DB 查詢只是它的 implementation detail。

  ## 1. 原本這個設計，真正要處理什麼？

  type WrappedReActDataFlow<'T> =
      ConcurrentQueue<ReActDataDirection * ReActDataStream<'T>>

  「集中保存有方向、有順序的 typed 資料，由一個 actor 寫 DB」很合理。需要補清楚的是：

  • Dequeue 不等於成功保存。
    先 dequeue、尚未 commit 就 crash，資料會遺失。改成 peek → commit → dequeue 可以改善這個窗口，但整個 process 掛掉，尚未持久化的記憶體資料仍會消失。必須定義
    何時回覆「已保存」，以及未確認的資料如何重送、去重。

  • 待寫入 queue 與永久歷史不是同一個生命週期。
    作為工作 queue，成功後 dequeue 正常；作為整段歷史，dequeue 就不適合。可以讓 DB journal 保存完整歷史、queue 表示待處理部分。若刻意保留全部記憶體歷史，也可
    以，但要接受記憶體持續增長。這是同一條資料流的不同保存方式，不需要再建立一堆 domain records。

  • 順序與方向需要共同基準。
    In／Out 相對誰？我理解應以 main wrapper 為基準。多個 participant 同時產生資料時，中央 actor 應決定該 flow 的順序；queue 的 FIFO 本身不會推導 causality。

  所以，原設計需要精修，並沒有充分理由直接讓 WrappedReActDataFlow 這個概念消失。

• ### 1. 你記得對，可以有多個 edge

  FSharp.FGL 有兩種表示：

  • 一般 Graph：不允許同一對節點重複加邊。
  • ArrayAdjacencyGraph：支援 multigraph，有 GetEdges(source, target) 可以取兩個節點間的多條邊。官方說明

  所以，不能因為我先查到一般 Graph 的限制，就要求每筆訊息一定變成節點。 participant／wrapper 作為節點、往返訊息作為多條 edge，是成立的。

  ### 2. 我贊成使用 FGL 原生 edge，移除重複的 from／to

  FGL 原生的 labeled edge 就是：

  type LEdge<'Vertex, 'Edge> =
      'Vertex * 'Vertex * 'Edge

  也就是「來源、目的、內容」。可以直接以它作為單筆路由資料，不必再在 payload 裡重複保存來源與目的。原始型別定義

  我建議的責任是：

  • edge endpoints：唯一的 routing from／to，使用 logical participant identity，不使用 ActorRef／Process。
  • edge label：保留事件內容、StreamId、causedBy、StartTurn／SteerTurn、Cot／Work／End 等語意。
  • 整張 graph：ReActLoopHandler 持有的累積狀態，不是每次訊息都傳整張 graph。

  這樣流程就是：

  原生 edge 進 mailbox
  → persist 成功
  → 加入 handler 持有的 graph
  → routing／user output

  mailbox 處理待辦，graph 保存記憶體歷史，因此不必另外保留 CQ 才能讀歷史。 我前面把「保留記憶體歷史」說成「必須保留 ConcurrentQueue」，確實綁得太死。

  外部仍透過 ReActLoop 取得資料；ArrayAdjacencyGraph.GetEdges() 本身就回傳 array，整理時再依 StreamId 排序，不必每次都查 Persistence.Query。實作來源

  但不能只是把目前型別外面包一層 LEdge，有三處要逐段整理：

  1. 現在 AgentCot／AgentWork 裡面是 ReActData[]；若各項目的端不同，就需要多條 edge，不能整包共用一個目的端。
  2. 原本 fromWrapper 註解是 reply-back 路徑。若 reply-to 不等於來源，這個語意不能隨 from／to 一起刪掉。
  3. ArrayAdjacencyGraph 要求 edge label 支援 equality，而且取得全部 edges 時會去重；因此必須保留唯一 StreamId，不能把兩次相同內容的訊息合掉。

  ### 3. 多主題與 compact 也能接在這個表示上

  同一對 participant 的多條訊息，可以屬於不同主題；主題不能只靠 participant 身分判斷，仍要明確記錄訊息的主題歸屬。

  之後便能選取某主題截至某個 StreamId 的資料，依人的指令交給獨立 COT participant 整理，再把摘要送給 main participant。摘要需要記錄涵蓋哪些原始事件；compact 改
  的是後續使用的 context，不直接刪掉 durable 原始歷史。

  所以我支持改成 FGL-native 的 edge 表示，但先不直接修改 Contract。下一小段先整理「單筆 edge 的 label 保留哪些現有 DU 內容」，把重複 from／to 拿掉，不新增一堆
  record。

• 要改的是 ReAct 的資料表示、記憶體 graph 的讀取規範，以及對應的版本化入口。Versioned、VersionRegistry、FeasibleFun、FodexFun 基底不需要重新設計。

  依檔案與宣告順序，我建議以下範圍。這是提案，尚未改碼。

  ## 1. Fodex.Supervisor.Contracts.fsproj

  加入 FGL 的依賴：

  • FSharp.FGL：原生 vertex／edge 型別。
  • FSharp.FGL.ArrayAdjacencyGraph：支援同一對節點多條 edge 的 graph。

  這代表 FGL 成為 Contract 的架構依賴，就像目前保留 IActorRef 一樣，不再另外造一套 graph DTO。

  ## 2. concepts.fsx 前段：版本化入口

  增加一個「讀取記憶體 graph」操作，暫名 ReadDataFlow。

  照既有模式補齊：

  • LiteralsMod：function target 名稱。
  • command／版本參數：允許指定版本。
  • TypesMod：操作的泛型函數形狀。
  • 後段 ReActLoop：registry resolve、建立時 pin、default member。

  不新增 Registry 類別或 Runtime 類別。 操作仍經 FeasibleFun → FodexFun。

  ## 3. 核心資料型別：這是主要修改區

  ### 3.1 先確定 vertex 身分

  graph 使用穩定的 logical identity，不使用 ActorRef 或 Process 作為 key。

  若現有 participant 身分沒有涵蓋 user，最小形狀可以是：

  type ReActEndpoint =
      | Human
      | Participant of ReActParticipant

  participant 的註冊與操作仍然使用 IAgent；這不是把 IAgent 改回 Agent，只是 graph 不保存整個可執行物件。

  ### 3.2 ReActData<'T> 移除路由欄位

  目前這類內容：

  WrapperToNatives (..., toParticipant, fromWrapper)
  NativeToNative (..., toParticipant)
  MainWrapperToWrapper (..., toWrapper)

  不再各自保存 from／to。方向交給原生 edge，payload 只保留：

  • 使用者的 typed prompt。
  • 要交給 agent 的內容與 StartTurn／SteerTurn。
  • agent／wrapper 產生的內容。

  因此部分「以方向命名」的 DU case 可以合併，不只是刪掉 tuple 最後幾項。

  但 fromWrapper 原本還有 reply-back 語意：能從 edge source 或 topology 推得才刪；推不得就保留明確的 reply-to，不能把不同語意一起丟掉。

  ### 3.3 原本的 stream DU 改作 edge label

  原本 ReActDataStream<'T> 的分類仍有用途：

  • HumanInit
  • AgentCot
  • AgentWork
  • StdOut
  • StdErr
  • AgentEnd

  它們保留為事件內容 DU，暫名 ReActEvent<'T>；StreamId、causedBy 也保留。

  然後：

  type ReActDataStream<'T> =
      FSharp.FGL.LEdge<ReActEndpoint, ReActEvent<'T>>

  這裡才是真正讓 ReActDataStream 成為 FGL-native。

  要一起修正的是目前 AgentCot／AgentWork 裡的 ReActData[]：若項目有不同目的端，就拆成不同 edge；不能移除內層目的端後，又把整包塞到一條 edge。

  ### 3.4 WrappedReActDataFlow 改為原生 graph

  它表示 handler 持續維護的記憶體狀態，不再是 ConcurrentQueue。

  最小提案是：

  type WrappedReActDataFlow<'T when 'T : equality> =
      FSharp.FGL.ArrayAdjacencyGraph.ArrayAdjacencyGraph<
          ReActEndpoint,
          unit,
          ReActEvent<'T>>

  這裡 node label 暫用 unit，避免先發明另一套 participant record；節點身分在 key，活著的 IAgent 仍由既有 participant binding 管理。

  有一項必須明講：這個 graph 要求 edge label 支援 equality，因此會帶入 'T : equality 限制。 不能偷偷讓這個限制擴散到其他公開型別才告訴你。FGL 實作

  ## 4. ReActLoop 的規範與 member

  三個操作的職責分清楚：

   操作                    規範
  ━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   RouteReActDataStream    接收原生 edge；成功持久化並更新記憶體 graph 後，才視為成功
  ──────────────────────  ────────────────────────────────────────────────────────────
   Collect                 維持讀持久化資料，取得原生 edges
  ──────────────────────  ────────────────────────────────────────────────────────────
   ReadDataFlow            讀 handler 當下已保存資料所形成的 graph 快照

  ReadDataFlow 的提案形狀：

  abstract member ReadDataFlow:
      FeasibleT<
          ReActParticipantSessionId,
          WrappedReActDataFlow<'TypedCmdToWrapper>,
          exn>

  Contract 另外寫清楚幾個不變量：

  • handler 持有持續更新的 graph；外部透過 ReActLoop 讀，不直接操作 handler。
  • 回傳讀取結果不得讓呼叫端修改 handler 內的資料。
  • participant 停止或移除，不代表刪掉它的歷史節點與訊息。
  • 改成通用 edge 後，原本允許／禁止的通訊拓撲仍須驗證。
  • StreamId 是事件身分；同來源、同目的、同文字的兩次訊息不能合併。

  Contract 不指定一定使用 Akka.Persistence。具體 journal、serializer、recovery／query，仍由各版 FodexFun 實作。

  ## 5. 這次不能迴避的相容性問題

  把公開 DU 改成 LEdge，是 breaking change，不是單純替換實作。

  現有 V100／V101 函數與 quotation 不能只靠換註冊版本，就自動吃新的 CLR 型別；舊 DB 資料也不會自動補出原本沒保存的 endpoints。這些必須保留舊 reader 或安排明確
  的轉換，不能假裝 hot plug 已經處理了。

  主題歸屬、摘要涵蓋哪些事件、compact 規則，則先不混進這一波。FGL-native 提供表示基礎，但不等於這些功能已完成。

  我建議先精修第 3 項的型別形狀，尤其是「一筆 edge 的粒度」與 equality 限制；確認後，再按編譯順序逐檔落實，不同時大改整個實作專案。
