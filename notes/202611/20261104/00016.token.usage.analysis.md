# M018：1+N 協作的 token 使用分析

日期：2026-11-04。性質：已核實歷史 snapshot 的解讀，非本文件任務的即時統計。

本文依本次指定內容忠實整理主控上一則分析，採用主控先前從本地 session token_count 核實的固定 snapshot 與既定範圍；本次文件任務不重新讀取 rollout、不重算現時 session，也不複製原始 history。可供未來 harness 採用的守則另見[節省計畫](00016.token.usage.save.plan.md)；該計畫尚未實作、安裝或啟用。

## 主控分析的核心結論

這次協作的 context 隔離、專項分工與交叉審查有效：開發、測試與文件可以各自持有必要細節，主控不必親自處理全部實作；不同角色也能發現正式入口、測試範圍與交付依賴的落差。但沒有同等條件的單 agent 對照，**尚不能證明總 token 因此節省，也不能宣稱節省百分比**。

依已核實的主控對帳摘要，四輪共十一單全部收齊。這證明本次收件閉環完成，不代表沒有等待、返工或額外控制成本；本文件沒有足夠逐單資料去分攤十一單的 token，也不補造 orderId 或逐單帳單。

成本增加的來源包括等待期間的模型喚醒、長派工指令、反覆讀取規範與交接、文件稽核及後期依賴返工。等待經過多少秒本身不等於多少 token；只有等待伴隨的實際模型請求、重新注入的上下文與輸出，才會出現在模型用量中。降低這些成本，應改善狀態傳遞與確定性處理，不應刪去必要進度回報、品質驗證或工作區要求。

## 統計範圍與限制

- **main**：M018 開始，至交付完成後第一次「請回顧」之前的累計差。本文件任務及之後對話不在該窗口。
- **sub-4／sub-5／sub-6**：各該工作 session 的累計，包含 bootstrap；不是嚴格只歸屬某一 order 的切帳。與 main 的窗口口徑不同，解讀合計時必須保留此限制。
- `input` 包含 `cached_input`；本 snapshot 的未快取輸入為 `input - cached_input`。
- `output` 已含 reasoning，不得再把 reasoning 加進 output 或 total。未提供 reasoning 的獨立數值，不自行拆分。
- `last_request_input` 只表示最後一次請求的 input 負荷，非累計或 peak 欄位；本報告未另作峰值核實，不判定其數值是否恰與已觀測最大值相同，也不代表峰值記憶體。
- 曾觀察到 context metadata 為 **475000**。這只是該歷史環境的 metadata 觀察，不是所有模型、所有 session 的規格，也不保證實際可用輸入或輸出預留量。
- 沒有價格、實際計費規則或可比較的單 agent 基線，因此不換算金額，也不以 cache hit 或模型角色猜測成本。

```text
uncached_input = 91,402,179 - 90,459,520 = 942,659
total         = 91,402,179 + 435,578    = 91,837,757
cache hit     = 90,459,520 / 91,402,179 × 100%
              = 98.968669%（顯示至小數六位）
```

`total` 是這組 input 與 output 的統計合計，cached 已在 input 裡，reasoning 已在 output 裡。兩者都不再重複相加。

### 這些數字能說什麼

高 cache hit 顯示多數輸入按這份 provider 統計被計為 cached；它不等於高比例「省下所有費用」，也不證明拆成更多 worker 比單 agent 更省。仍有 942,659 uncached input 與 435,578 output，且 cache 條件、單價與對照工作量未齊備。

91,402,179 的累計 input 不代表有這麼多唯一新內容。相同歷史、工具定義、指令或摘要可能跨請求重複計入；cached input 也仍屬請求輸入計數。反過來說，uncached input 同樣不是去重後的新增內容量，不能直接當作新增知識或新增使用者文字。

sub-6 的累計 input 與最後一次 input 在此表最高，可以把文件角色的重複閱讀與上下文負荷列為改善重點；但不能只憑這張表判定其每個 token 都可移除，或把角色數量、最後一次 input 直接當作浪費與記憶體排名。本報告未另核實逐輪歸因或峰值，也沒有反事實對照。

## 優點、成本與改進方向

| 觀察 | 優點／必要性 | 成本或限制 | 改進方向 |
|---|---|---|---|
| 專項 context 隔離 | 開發、測試、文件各持有必要專業內容，支援並行與獨立判斷 | 重疊規範、契約與背景可能被各 session 重讀 | 共用契約一次版本化引用，後續只傳差異與必要證據 |
| 交叉審查 | 有助發現依賴綁定、入口與驗證範圍落差 | 若每輪每人都全文複查，會放大成本 | 按風險與 AC 指派必要交叉審查，不預設人人重讀全案 |
| 四輪十一單收齊 | order 收件閉環沒有被省略 | 輪次本身不代表效率，等待喚醒與補交接仍可能增加模型回合 | 保留同輪收齊硬邊界；由 runtime 管理等待、對帳與狀態顯示 |
| 長指令與重讀交接 | 能保留權限、owner、失敗與驗收邊界 | append 長文件反覆注入，最後一次請求 input 也偏大 | 小型 ready/result 卡引用不可變證據；只有變更或缺口才讀對應段落 |
| 文件稽核、log、Git 收尾 | 秘密、dirty ownership、append-only 與追溯規則不能取消 | 重複摘要、反覆稽核和自記 metadata 容易增加輸入與輸出 | harness 一次產生小摘要，單一 index owner，最後回讀存指定文件；不弱化 verifier |
| 後期依賴返工 | 測試揭露了 compile／verify-only 無法代表真入口成功 | Argu／MCP、測試入口 pin 與共享 dirty API 邊界較晚釐清，帶動多角色重讀與重驗 | 先打通正式入口最小真鏈與版本，再擴展並行驗收 |

這裡的依賴案例只作改善方向，不重述完整技術報告：正式 source、測試專用 bootstrap、目前 workspace 與 clean checkout 是不同證明範圍。文件提前寫骨架有用，但終版宜在必要結果收齊後集中整理，避免每輪反覆重寫整份結論。

上述成本分類是主控觀察與交接可支持的質性分析，**不是已量測的逐類 token 分帳**。不能替每一類成本配置臆測百分比，再相加成預期節省。

## 未來重現統計的原則

本節描述將來如何重現；本次不執行原始歷史搜尋。

1. 先固定 scope、session identifiers、起訖邊界與統計 schema。明列 controller、所有 workers、bootstrap、交接、取消、重試與 compaction 是否納入，保留 main 窗口與 worker session 累計的差異。
2. 對 cumulative usage 取符合窗口的 end−baseline，不能把每筆 cumulative snapshot 再加總。若 counters 非單調、發生 reset 或 schema 改變，依可辨識的 epoch 分段；保留 reset／缺口，不用負數、任意歸零或全段 max−min 補出看似完整的數字。
3. 按原始 provider 欄位確認 cached 是否包含於 input、reasoning 是否包含於 output；只有定義相容的欄位才相加。reasoning 若是 output 子集，只另列分析，不再加進 total。
4. 單次 input、累計 input 與實際觀察到的單次最大值分開。未收集峰值就標未收集，不把 last input 當峰值或把 context metadata 當記憶體。
5. cache hit 必須用可比較的 input 作分母；金額須有相符價格與計費規則才可計算。本組資料不提供金額估算。
6. 以同 AC、版本、品質、權限及可比較 cache 條件，進行多次單 agent／最少必要 N 的對照。若缺少合法可比拓撲或基線，就維持「未證明總 token 節省」，不能只以高 cache hit 或更多 worker 宣告成功。
