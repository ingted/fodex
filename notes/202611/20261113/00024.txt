    132 +## A2. 執行邊界：何處 await、何處容許同步
    133 +
    134 +1. SQL handler V403 已採真正 async SQL，服務歷史查詢必須一路 Task／await，不可 `Task.Run(fun () -> loop.Collect ...)`。
    135 +2. Wrapper407、Native302、OwnedProc302 的現有同步相容區域各用自己的真實 PinnedDispatcher。不能共用有限 worker pool；不能拿 default-blocking-io-dispat
         cher 別名冒充隔離。
    136 +3. FodexAgent.CreateReActLoop／CreateWrapper 的 Contract 仍是同步。外層服務只在建立一次資源時，使用 `Task.Factory.StartNew(..., TaskCreationOptions.L
         ongRunning, TaskScheduler.Default)` 承接這段同步初始化。不得每筆 prompt／每次 collect 建 thread。
    137 +4. SQL provisioning／首次 registry 載入等同步工作也在這個建立邊界內，不能在 service root mailbox 的呼叫前綴先做掉。
    138 +5. 完成建立後，IAgent Start／Stop 使用 async pin；Collect 使用 async pin。服務 actor 自己只更新少量狀態、啟動 async operation、接收 completion。
    139 +6. 不宣稱整個產品「完全無同步」。保留的同步邊界有具體理由、dispatcher、測試；歷史 16:15 的 heartbeat warning 仍未證明唯一原因，不能以此宣告已定位。

    481 +## B4. `line_provider_fodex_v3_service.fsx`：admission與執行分開
    482 +
    483 +### B4.1 新API與次序（固定）
    484 +
    485 +```fsharp
    486 +member _.SubmitWithAsync(
    487 +    input: Ingress,
    488 +    work: RemoteWrapper -> Task<TurnReply>,
    489 +    ct: CancellationToken,
    490 +    ?reset: bool
    491 +) : Task<Task<string>>
    492 +```
    493 +
    494 +外層Task代表「取得或完成durable admission／inFlight reservation」；內層Task是已接受工作的最終結果。它不是兩次生成，也不是給人操作的兩層API；這個分離
         讓IngressActor只await admission、不await模型。
    495 +
    496 +- 使用一個`SemaphoreSlim(1,1)`作service admission gate，保留原本全域`lock gate`的admission順序，但不占actor/threadpool worker。
    497 +- admission gate只涵蓋metadata／claim／reservation，不涵蓋native generation或等待上一個turn完成。這次不新增per-conversation actor或第二套queue。
    498 +- 原`lock gate`仍可用於極短dictionary/counter快照，不做SQL、不await、不呼叫可能同步執行外部IO的factory。
    499 +- 全域admission gate會讓一筆SQL metadata暫慢時後續admission排隊；這是保留原序列邊界的明確取捨，不承諾不同conversation的admission可越過它。不同convers
         ation已接單的生成仍並行。
    500 +
    501 +**新route精確順序**：
    502 +
    503 +1. await admission gate；檢查stopping/reset/capacity；算payloadHash。
    504 +2. 同route inFlight：驗hash，回同一inner Task，不claim、不再次prepare native。
    505 +3. await LookupAsync：completed則回原Reply；queued/working無本機inFlight則fail-closed，不能當新工作。
    506 +4. await MappingAsync、AcquireLaneAsync、AcquireAsync；保存取得的ownership以供失敗清理。
    507 +5. await Fence／FenceLane／Claim；此時SQL sequence已確定。
    508 +6. 在短lock中建立inFlight、tail、entry.Pending/pending以及runtime launch reservation；原子的memory publication不得被另一個admission越過。
    509 +7. 啟動entry runtime factory與該route work continuation；釋放admission gate；回inner Task。
    510 +8. work await previous same-conversation tail（前次失敗不永久毒化後續）；await fence/Working/runtime/work/Complete；不同conversation tail互不等候。
    511 +9. completion寫入durable SQL成功後才Complete innerTask；finally在短lock減counter／移inFlight／只刪仍指向本Task的tail。
    512 +
    513 +**禁止原本的缺陷**：在Claim成功前先啟動factory/native。如果claim失敗卻留下正在初始化的remote wrapper，必須清理或保留明確ownership，不能稱未接受而無人
         負責。
    514 +
    515 +在claim前的失敗：釋放本次新取得且未共用的lease/lane、還原reservation；不啟動native。
    516 +Claim後的失敗：不把route刪成可重送；標記indeterminate或保留可確認狀態，completion失敗；只有證明相同route已completed才能取原答覆。
    517 +
    518 +### B4.2 cancellation、sweep、reset、stop
    519 +
    520 +- `ct`只影響尚未取得admission gate的waiter及明確未接受階段。已開始可能寫入的admission不隨RN Ask timeout取消；先完成／確認durable結果，再回報。已接受i
         nnerTask不因caller停止等候而被取消。
    521 +- native turn使用既有TurnTimeout／wrapper cancel政策，不能把LINE十秒觀察時間變成native timeout。
    522 +- 一次只有一個sweep。保留Interlocked防重入，但用`currentSweep: Task`保存當次completion，DisposeAsync直接await；移除`while sweeping ... Task.Delay 10`
         。
    523 +- sweep選取entry只做短lock，實際await ReleaseAsync在lock外；新admission見Retiring仍遵原backpressure。
    524 +- ResetAsync／RecoverAsync／SelectAsync改為真正async Store API；與admission gate協調互斥，不能與新claim交錯覆蓋generation。reset標記後釋放gate再做rem
         ote close；其他admission依reset標記拒絕，不在gate內等模型。
    525 +- `DisposeAsync`是停止本地等待、清lease／lane，不等於關遠端native；`StopOwnedAsync`才對SQL記錄的owned WSID逐一close並確認。保留這個區分。
    526 +- Stop順序：BeginStop拒絕新admission→等待已進入的admission完成／固定inFlight集合→await本地tasks/sweep→關閉owned wrapper→完成runtime-close SQL記錄。錯

    527 +- close/reset失敗保留原WSID/Generation供重試；不以建立新WSID消除錯誤。
    528 +- SQL synchronous constructor移除後，Service接收已InitializeAsync的Store（新增constructor必要參數），不要每個Service重做DDL。tests同樣先初始化。

         imeout也可能是此型別。

    559 +ReceiveAsync在prepare/admission期間會暫停該actor處理下一筆mailbox，**但會釋放dispatcher worker**。這是為保持目前入口接收順序；不新增ticket-reorder ac
