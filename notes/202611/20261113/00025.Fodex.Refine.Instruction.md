# Fodex／LINE v3 refinement：change specification 與 software design

日期：2026-11-13。讀者：接手本輪工作的 workhorse agent（包含切換為 gpt-6.1-sol 後的自己）。

本文是實作前的固定設計，不是已完成報告。程式碼片段用於限定簽章與控制流程；仍須依既有 F# 型別、編譯順序完成編譯。只因文件寫了某個版本，不代表該版本已建立、註冊、測試或部署。

## 檔頭摘要：先看這一頁

**產品目標**：LINE Official Account 是穩定的人機介面。LINE 訊息由 .NET code 確定地送進 Fodex wrapper，收到其 native 的結果；不依靠模型操作 COMM、不依靠模型正確 blocking wait。支持 codex／agy、main／sub、wrapper／raw 的既有能力。

**目前缺口分成兩章，禁止混為一談：**

1. **A 章，Fodex 服務接線**：內部新元件已完成一批，但 CLI 的 service 分支仍 pin 舊 factory。完成 service-only factory V408、ServiceWrapper V103、ServiceSupervisor V102、ServiceHost V104、ProgramV410；歷史查詢改為真正 await。保持 console 分支、公開 Contract 與 service wire v1 不變。
2. **B 章，LINE 端剩餘阻塞路徑**：v3 載入自己複製、改名的 almighty 副本；不再依賴原 almighty 檔案。修正 `PrepareAsync(...).GetResult()`、同步 SQL admission、SQL 在 `lock gate` 內執行等問題。維持 durable route 去重、FIFO、owner fencing、圖片及 `/next` 行為。

**使用者最後確認的套件規則，覆蓋先前「全部最新」的概括說法：**

- `FSharp.Core`、`FSharp.Compiler.Service` 不硬升；保留既有相容配套。
- 已固定的 `FAkka.*`、`PulseTrade.*` 不升版、不重建發布。
- 上述固定套件所依賴的 X/Y 也受保護：不能因 X/Z 更新，就在 consumer 額外 `#r X/Z` 強行覆蓋。
- 只有不破壞上述依賴配套的第三方套件才更新至最新 stable。不得以「NuGet 接受 higher version」取代相容性與使用者限制。
- 不因 LINE 的套件更新，順手更新 Fodex 的全部套件。兩者是不同程序、不同編譯／載入閉包。

**工作方式**：依本文順序完成小單元及相應測試，交由 basder review 固定候選；asteer 負責 G 槽 v3 腳本，fodex 負責 Fodex 實作與唯一 live 操作。不要讓兩人同改同檔。不新增 Demo 專案、不新增另一套 actor runtime／queue／harness。

**這份文件交付不等於恢復實作／部署授權**：寫文件時仍在暫停狀態。收到使用者恢復指令才執行。不要為了「收尾」啟動建置、模型、服務或 LINE 測試。

### 0.3 不可變條件

- 公開 `Fodex.Supervisor.Contract` 本輪不改；不得偷偷加 abstract member。
- 新版 FodexFun 必須以 quotation 宣告、首次使用自動註冊到既有 registry，再經 `FodexFun`／`FeasibleFun.invoke` 執行。不得直接呼叫新版 module function 繞過 registry。
- `'Input -> 'Input -> Result<...>` 保持既有語意：input 送入吃 input 的函數。不要另造 callback binder 解釋這個型別。
- 不使用 `private`、`internal`、`[<RequireQualifiedAccess>]`。FodexFun 所在 module 使用 `[<AutoOpen>]`，延用 `Definitions.builtins`。
- `IAgent`／`FodexAgent` 使用 object expression。普通 Akka actor 繼承 `ReceiveActor` 不受此限制。
- 舊版本保留；用 fsproj `Link` 分組，不將新版覆寫回舊 Vxxx。舊 entrypoint 變成 `None + Archive`，不刪檔。
- 所有 actor message sender/context 在 receive 內取得；logger 來自該 actor 的 `ILoggingAdapter`，透過既有 `AkkaLoggerAdapter`／`toUL` 傳入 child context。不要自己 append log 檔。
- stdout/stderr 與 ReActEvent 分開；service JSON 不混入 native 原始 stdio。
- 不擅改模型、effort、sid、workdir、participant 編號／who；不以測試通過為由重置人類 session。
- 所有 shell 使用既有 `Read-CodexStdout`，一次 capture 小於 20KB，不平行使用 guard。不要重讀 output-guard skill。
- COMM 如需收訊，一次 `comm_inbox_read_chunk(participantId="fodex", count=20, maxResponseUtf8Bytes=16000)`；依 hasMore 續批，preview 使用 readToken。禁止逐筆 get_next_message 迴圈。

### 0.4 責任歸屬：本輪確定放哪裡

| 能力 | 唯一責任位置 | 本輪處置 |
|---|---|---|
| 建 wrapper、native、sub；設定 provider／model | FodexAgent／IAgent／ReActLoop 及實作 registry | v3 只送既有 service 指令，不建立 native process |
| native cancel、Stop、compact、資源清理重試 | Fodex.Supervisor | 使用既有 Native302／Wrapper407；不能讓 v3 以 PID kill 補假成功 |
| wrapper lifecycle、service bridge、close ACK | Fodex.Supervisor | A 章補完，ACK 必須代表真正完成所宣告的動作 |
| ReActEvent SQL 保存、graph、完整歷史／cursor 查詢 | Fodex.Supervisor | async Collect 接到 service receive；v3 不讀 Fodex graph 私有資料 |
| service 的 request/cause correlation、訂閱與等候完成 | Fodex.Supervisor | 保留 wire v1、ServiceSupervisor 的職責與 FIFO admission |
| LINE route、hash、generation、LINE redelivery／reply exactly-once | LINE v3 | 保留 LINE SQL store；不能移進通用 Fodex wrapper |
| account/source/conversation 到 WSID 的對應、LINE 選定 target | LINE v3 | 保留 mapping，不把 WSID 假裝成 Codex SID |
| `/next` 的已交付游標、LINE reply token、圖片權限與下載 | LINE v3／既有 RN Line package | 留在 B 章；沒有 LINE Push |
| Akka remoting client 的 encode／exchange／receive 分頁 | v3 transport adapter | 本輪保留薄 client；不新增 Fodex SDK project、不載入 Fodex exe assembly 到 RN |
| Windows PID/birth 額外驗收與部署 stop receipt | 既有 lifecycle／launcher | 保留作獨立驗收；不是 native lifecycle 的第二個實作 |

**確定需要改善 Fodex，而不能繼續堆在 v3 的部分**：建立／關閉 wrapper 的 ownership、失敗後可重試、非同步歷史查詢、service request correlation、native Stop 完成判定。全部在 A 章落實。LINE v3 不再加自己的 model wait loop、重建 Codex session、Process.Start 或另建 ActorSystem 去補這些能力。

**本輪不新增 service 協議操作**：現有 create／attach／send／send_wait／receive／close／list／shutdown 足夠此次整合。若測試發現既有操作不符合承諾，修 owner 端實作；不能先在 LINE 增加 workaround，再稱其為永久架構。跨 service restart 的完整 requestId 索引重建不是本次新功能；仍維持現有 cursor recovery／不確定工作 fail-closed，不偷偷自動重送。

# A. Fodex 服務接線

## A1. 現況與固定目標

現況：

```text
ProgramV409 service branch
  Service.Run 1.0.3
    Service.CreateSupervisor 1.0.1
    Service.CreateWrapper 1.0.2（外層 service factory signature）
      FodexAgent.Create 4.0.7
        loop 4.0.2 / manager 4.0.2 / wrapper 4.0.6
```

固定目標：

```text
ProgramV410 service branch
  Service.Run 1.0.4
    Service.CreateSupervisor 1.0.2（async-history signature）
    Service.CreateWrapper 1.0.3（外層 service factory signature）
      Service.CreateFodexAgent 4.0.8
        loop 4.0.3
        Service.CreateParticipantManager 4.0.3
        Service.CreateWrapper 4.0.7（內層 IAgent factory signature）
          Service.CreateNative / Service.CreateRaw 4.0.7
            Native302 / Proc302 / RPC101
```

`Service.CreateWrapper` 的兩個使用點，名稱雖相同，但 input/output type 不同，屬於不同 typed registry。禁止因看見相同 literal 就誤改成同一個 factory。新增測試必須驗證這個差異。

console 分支保持 `ConsoleHostFodexFunV408`／原 factory `4.0.6`；原 `FodexAgent.Create` 的 None 選版不受新 service target 影響。不要把服務修正順手變成 console 升版。

## A2. 執行邊界：何處 await、何處容許同步

1. SQL handler V403 已採真正 async SQL，服務歷史查詢必須一路 Task／await，不可 `Task.Run(fun () -> loop.Collect ...)`。
2. Wrapper407、Native302、OwnedProc302 的現有同步相容區域各用自己的真實 PinnedDispatcher。不能共用有限 worker pool；不能拿 default-blocking-io-dispatcher 別名冒充隔離。
3. FodexAgent.CreateReActLoop／CreateWrapper 的 Contract 仍是同步。外層服務只在建立一次資源時，使用 `Task.Factory.StartNew(..., TaskCreationOptions.LongRunning, TaskScheduler.Default)` 承接這段同步初始化。不得每筆 prompt／每次 collect 建 thread。
4. SQL provisioning／首次 registry 載入等同步工作也在這個建立邊界內，不能在 service root mailbox 的呼叫前綴先做掉。
5. 完成建立後，IAgent Start／Stop 使用 async pin；Collect 使用 async pin。服務 actor 自己只更新少量狀態、啟動 async operation、接收 completion。
6. 不宣稱整個產品「完全無同步」。保留的同步邊界有具體理由、dispatcher、測試；歷史 16:15 的 heartbeat warning 仍未證明唯一原因，不能以此宣告已定位。

## A3. 逐檔修改規格

### A3.1 `FodexAgentFodexFunV408.fsx`：完成既有草稿

位置：`Fodex.Supervisor/`。來源是 V407；V407 不改。

- version `System.Version(4,0,8)`；target 固定 `Service.CreateFodexAgent`。
- 同 input/output：`FodexAgentCreationV402 -> FodexAgent<string,obj>`，保留 object expression、arguments pin、node identity 檢查。
- `loop`：明確 pin `4.0.3` 的既有 loop target，不能 None。
- `CreateWrapper`：manager pin `ParticipantManagerFodexFunV403.target` `4.0.3`；IAgent factory pin `FodexFunRegistrationV407.targetServiceWrapper` `4.0.7`。
- manager operations/install/disposal 的既有 `4.0.2` 可保留：這是不同 operation，不是 manager constructor。禁止看到 V402 就全部字串取代。
- owner watcher 使用草稿中的 `fodex-wrapper-owner-v408` PinnedDispatcher，避免同步 gate 與建立／清理相互等候。
- `dispose`：使用 `wrapper.PinStopAsync(node, Some "3.0.1")()`，收到 Error 立即停止後續 destructive cleanup。保留 loop、binding、hub、資源 ownership；下一次 Close 重試同 factory。
- Stop 成功之後才 participant disposal、hub disposal、actor 結束。不得先清 dictionary 再聲稱 Stop 成功。
- 同一個尚未完成的 disposal task 重用；faulted/cancelled 後允許新一次 explicit Close。不得在 finally 將失敗狀態抹成 disposed。

**必改的停止完成邊界**：草稿最後的 `node.Stop`／PoisonPill 只是發出停止請求，不能讓外層 close/termination 測試誤以為全部已 Terminated。V408 在 native Stop、participant disposal、hub disposal 成功後，對 wrapper actor 及 ownedActors 的 distinct refs 使用 Akka `GracefulStop` 等待 Terminated（已終止的 ref 亦接受為完成）。先開始 termination observation 再等待結果，不先 node.Stop 後才嘗試建 watcher。全部共用一次有界 shutdown budget，不為每個 actor 重置完整 timeout。`disposed <- true` 移到所有 termination 完成之後；清理中拒絕新的 Create，不重新建資源。owner watcher 收到 Terminated 只啟動／重用 dispose Task並返回mailbox，不同步等待自己結束；避免自等 deadlock。停止任何一步失敗都保留已持有的 refs 與清理進度，後續Close只重試尚未完成的階段。這是本檔既有 disposal 的完善，不另建 runtime。

factory每次explicit Close的本地budget固定30秒，Stop開始即啟動Stopwatch，各階段只使用remaining。外層Host已有更短remaining時先回其timeout，但不能因此丟掉仍持有的factory／清理Task。逾時並不代表底層操作取消成功；重試先檢查同一pending Task，不並行發第二份Stop。

### A3.2 `ServiceWrapperFodexFunV103.fsx`：新的 async history seam

新增檔案，從 V102 保留設定驗證、logger、transport、SID、output sink、defaults precedence；不改原 V102。

在本檔 namespace 下，先宣告實作專案專用型別（不要放 Contract）：

```fsharp
type ServiceWrapperV103 =
    IAgent<string,obj>
    * (unit -> Task<Result<ReActDataStream<string> array,exn>>)
    * (unit -> Task)

type ServiceCreateV103 =
    FeasibleT<ServiceCreateInputV100,
              Task<Result<ServiceWrapperV103,exn>>, exn>

type ServiceSupervisorInputV102 =
    ActorSystem * UniContext * ServiceCreateV103 * bool * bool
```

沿用 `ServiceWrapperCreationV100` 作 input；version `1.0.3`，target 仍 `Service.CreateWrapper`。只有 output signature 改為 Task<Result<ServiceWrapperV103,exn>>。

建立流程固定如下：

1. parse override，只准既有 native/participant 設定；禁止 caller 改 database、network、output root。
2. 準備 ctx、catalog、hub URL、session／arguments；保持原先語意，不順手增加 model/list 呼叫。
3. pin `Service.CreateFodexAgent 4.0.8`，建立 factory，立刻保存 ownership reference。
4. 呼叫 `factory.CreateReActLoop`、`factory.CreateWrapper`。production caller 是 A3.4 的 Host make，其 LongRunning delegate 負責這段同步工作；Wrapper103 不另開第二條 thread。
5. `let! started = wrapper.PinStartAsync(node, Some "3.0.1")()`；檢查 Result。
6. 將 loop 的 async Collect closure 與 factory.DisposeAsync closure 回傳。

```fsharp
let collect () : Task<Result<ReActDataStream<string> array,exn>> =
    loop.PinCollectAsync(Some "3.0.1") session

let dispose () : Task =
    (box factory :?> IAsyncDisposable).DisposeAsync().AsTask()
```

Collect 取 SQL 完整歷史，不改成 graph snapshot；compact/prune 後 reconnect 仍能讀歷史。不要包 `Seq.toArray` 到同步查詢外面冒充 async。

**建立失敗的 ownership 規則**：create 失敗時 await 已取得 factory 的 DisposeAsync；cleanup 也失敗時不能只 log 然後丟失 factory。新增本檔內的 `ServiceCreateCleanupExceptionV103(error, cleanupError, retryCleanup: unit -> Task)`，作 Error exn 傳給 supervisor；它只攜帶未清理 ownership 的 retry callback，不是另一套 runtime。原錯誤與 cleanup error 均保留，對外 JSON 只輸出安全錯誤資訊，不序列化 closure。

Supervisor 見此 exception 保留該 callback，拒絕同 SID 的新 create/send，只允許 close 重試與錯誤查詢；重試成功才移除 failed bridge。這個額外型別有明確用途：避免初始化一半時 native／hub 成 orphan。Exception 類別的正常繼承可用，IAgent 仍用 object expression。

quotation 必須沿既有形式：

```fsharp
let quotation : Expr<ServiceWrapperCreationV100 ->
    FeasibleT<ServiceWrapperCreationV100,
              Task<Result<ServiceWrapperV103,exn>>,exn>> =
    <@ fun _ -> fun input -> create input @>
```

### A3.3 `ServiceSupervisorFodexFunV102.fsx`：await history，不在 actor 等模型

新增檔案，從 V101 複製；version `1.0.2`；target `Service.CreateSupervisor`；input 改為 `ServiceSupervisorInputV102`。

- resource 改成 `ServiceWrapperV103 option`。
- 新增最小 implementation message：`AsyncServiceCreatedV102 of Result<ServiceWrapperV103,exn>`。其餘 accepted/read/closed message 儘量重用 V100；不要複製整套 public protocol DU。
- `readHistory` 回傳 Task<Result<edge array,exn>>。
- `pump` 保持 admission 一次一筆：await before history → await wrapper.Request → await after history → 找到對應 HumanInit cause → post ServiceAccepted。
- 當前 pump 完成之前不開下一個 pump，避免兩個 caller 取到相同 baseline 配錯 cause。這只序列化接單，不等待 native AgentEnd。
- `beginRead` 真正 await reader，再 post `ServiceReadCompleted`；移除只為包同步 Collect 的 Task.Run。不在 mailbox 中 GetResult。
- background task 不修改 submissions、waiting、resource、observed 等 actor-owned state；捕捉必要 immutable refs，結果回 mailbox 更新。
- continuation 不重新讀 Sender；一律使用接單時捕捉的 recipient/self。
- close 成功仍先完成 dispose，再終止 bridge；shutdown 等 children 真正 Terminated。close 失敗保持可定位、可重試，不向 caller 回假成功。
- 若 A3.2 回傳 create-cleanup exception：設置 failed-create 狀態及 cleanup callback；同 SID create/attach/send 回原失敗，不再建立第二份資源。close await retry callback，成功後結束 bridge；失敗保留 callback。
- `handle`分支順序固定：先處理failed-create的close／拒絕其他操作，再處理一般stopping，最後才進入resource.IsNone的lazy create。不能讓close因resource=None而重新觸發create。新AsyncServiceCreatedV102(Error cleanupException)回覆並清空本次deferred callers，但不self-stop；只有沒有殘留ownership的一般create failure才沿原失敗回覆與bridge清理行為。
- client disconnect 只解除 subscription，不 Stop wrapper。
- preserves：send_wait、receive(waitMs=0/有限等待)、cursor、requestId 不符、同 ID 不同 text、event filtering、json/plain。
- `--json` event payload 維持原格式，不把 exception stack、stdio 或診斷字串混入輸出。

本檔不新增保存所有 event 的 queue，不複製 SQL store，不建立另一層 model execution state machine。

### A3.4 `ServiceHostFodexFunV104.fsx`：唯一 service 組裝點

新增自 V103，version `1.0.4`，target `Service.Run`，input 沿用 `ServiceHostInputV101`。

- `make` 型別 `ServiceCreateV103`，pin ServiceWrapper `1.0.3`，output 必須寫完整 typed signature。
- root pin `ServiceSupervisorInputV102 -> IActorRef` `1.0.2`。
- 同一 service 只建立一個 ActorSystem；`--akkaname`、`--akkaport`、`--mcpport` 等既有參數不改。
- `connection.Value` 若涉及同步 SQL provisioning，不在收到 create 的 actor worker 前綴求值；放在 A2 的一次性 LongRunning 初始化中。禁止根本沒建立 wrapper 就連 DB、起 native。
- **LongRunning 只設在 Host make；Wrapper103 本身不再 LongRunning。** Host delegate 先同步取得connection setting，再透過registry invoke Wrapper103；Wrapper103的同步factory建立段必須位於它的first await之前。後續Start／cleanup是task await，不能在continuation又執行同步Create。獨立Wrapper103單元測試由一般test driver呼叫，不能直接從actor mailbox呼叫。這是該內部factory的明確呼叫契約，不另增helper框架。
- supervisee create/attach 的 wire 語意不變。ServiceMcp V100 只消費既有 wire，不因 host 升版跟著重寫。
- shutdown 與 Ctrl+C 沿用同一清理路徑、共用剩餘 budget；failure 不回成功 exit code。
- ready 輸出仍寫既有 output channel，啟動時不建立 native；預設 stdout JSON 保持潔淨。

**LongRunning 形狀**（Task factory overload 在編譯時須明確，不能誤留 Task<Task<_>>）：

```fsharp
Task.Factory.StartNew(
    (fun () -> task {
        // 同步 provision／registry 初始化只在 first await 之前。
        let cs = connection.Value
        let create = (* typed registry pin ServiceWrapper 1.0.3 *)
        return! create(node,ctx,cs,options,input) |> required
    }),
    CancellationToken.None,
    TaskCreationOptions.LongRunning,
    TaskScheduler.Default).Unwrap()
```

`CancellationToken.None` 是 scheduler token，確保已接管 ownership 的 delegate 一定執行清理；業務 cancellation 仍由既有生命周期控制，不等於忽略 cancel。

## B3. `line_provider_fodex_v3_store.fsx`：真正 async SQL

此檔屬LINE metadata，不搬進Fodex。table schema、payload hash、Generation/Owner/RuntimeOwner、applock命名、transaction fence、OutputCursor/Delivered語意都維持。

### B3.1 API定案

- Store constructor只保存設定，不執行schema SQL。
- 新增`InitializeAsync(ct): Task<unit>`，在runHost建立Service前await一次；與現有Schema transaction/applock一致。失敗不能留下「已初始化」flag，下次可重試。
- `connectAsync(ct): Task<SqlConnection>` 使用OpenAsync；Pooling=false、ConnectRetryCount=0保留。失敗必Dispose。
- 原Store各方法改成同名加Async、末尾ct參數，原result外包Task：AcquireLaneAsync、FenceLaneAsync、LookupAsync、MappingAsync、AcquireAsync、RuntimeMappingsAsync、AcquireRuntimeCleanupAsync、CompleteRuntimeCloseAsync、FenceAsync、ClaimAsync、WorkingAsync、CompleteAsync、OutputPositionAsync、IndeterminateAsync、ReleaseAsync、ResetAsync、ProvenanceAsync、MappingsAsync、SelectedAsync、RouteIdentityAsync、SelectAsync、CompleteResetAsync、RecoverAsync。
- 所有production callsites／tests改用Async方法；不留下原同步方法以GetResult轉接的新actor路徑。
- 執行器：OpenAsync、ExecuteReaderAsync、ReadAsync、ExecuteScalarAsync、ExecuteNonQueryAsync、BeginTransactionAsync、CommitAsync／RollbackAsync。parameterized SQL不變。
- transaction包住的多句SQL仍同一transaction；不得拆成幾次獨立await破壞atomicity。
- cancellation在已送出寫入後可能是unknown commit，不自動重送SQL或native；透過既有route/fence查核，無法確認則保持indeterminate。

### B3.2 Connection併發與釋放

現有`lock connection`不能包await，也不能刪掉後讓兩個command共用同一SqlConnection。

- 新增LINE實作內的`OwnedSqlConnection`小型資源型別：持有`SqlConnection`與`SemaphoreSlim(1,1)`，提供`UseAsync`及`DisposeAsync`。用途只保護session-owned applock connection，不成為通用DB framework。
- `Lease.Connection`及conversation lane改持有這個資源。`UseAsync`取得gate後await command，finally Release；DisposeAsync同樣取得gate，標記closed並關閉physicalconnection，之後UseAsync明確ObjectDisposed。
- 不在operation進行中Dispose semaphore；不讓waiter因Dispose gate變成無法釋放。closed state與connection生命週期受同一gate保護。
- reader在釋放connection gate前Dispose；不能將live SqlDataReader傳出給caller。
- 一般短連線以use/use!持有，不加入全域cache。
- release失敗保留可診斷owner/fence狀態，但仍確保已不再使用的physical connection被清理；不能把session applock連線送回pool。

## B4. `line_provider_fodex_v3_service.fsx`：admission與執行分開

### B4.1 新API與次序（固定）

```fsharp
member _.SubmitWithAsync(
    input: Ingress,
    work: RemoteWrapper -> Task<TurnReply>,
    ct: CancellationToken,
    ?reset: bool
) : Task<Task<string>>
```

外層Task代表「取得或完成durable admission／inFlight reservation」；內層Task是已接受工作的最終結果。它不是兩次生成，也不是給人操作的兩層API；這個分離讓IngressActor只await admission、不await模型。

- 使用一個`SemaphoreSlim(1,1)`作service admission gate，保留原本全域`lock gate`的admission順序，但不占actor/threadpool worker。
- admission gate只涵蓋metadata／claim／reservation，不涵蓋native generation或等待上一個turn完成。這次不新增per-conversation actor或第二套queue。
- 原`lock gate`仍可用於極短dictionary/counter快照，不做SQL、不await、不呼叫可能同步執行外部IO的factory。
- 全域admission gate會讓一筆SQL metadata暫慢時後續admission排隊；這是保留原序列邊界的明確取捨，不承諾不同conversation的admission可越過它。不同conversation已接單的生成仍並行。

**新route精確順序**：

1. await admission gate；檢查stopping/reset/capacity；算payloadHash。
2. 同route inFlight：驗hash，回同一inner Task，不claim、不再次prepare native。
3. await LookupAsync：completed則回原Reply；queued/working無本機inFlight則fail-closed，不能當新工作。
4. await MappingAsync、AcquireLaneAsync、AcquireAsync；保存取得的ownership以供失敗清理。
5. await Fence／FenceLane／Claim；此時SQL sequence已確定。
6. 在短lock中建立inFlight、tail、entry.Pending/pending以及runtime launch reservation；原子的memory publication不得被另一個admission越過。
7. 啟動entry runtime factory與該route work continuation；釋放admission gate；回inner Task。
8. work await previous same-conversation tail（前次失敗不永久毒化後續）；await fence/Working/runtime/work/Complete；不同conversation tail互不等候。
9. completion寫入durable SQL成功後才Complete innerTask；finally在短lock減counter／移inFlight／只刪仍指向本Task的tail。

**禁止原本的缺陷**：在Claim成功前先啟動factory/native。如果claim失敗卻留下正在初始化的remote wrapper，必須清理或保留明確ownership，不能稱未接受而無人負責。

在claim前的失敗：釋放本次新取得且未共用的lease/lane、還原reservation；不啟動native。
Claim後的失敗：不把route刪成可重送；標記indeterminate或保留可確認狀態，completion失敗；只有證明相同route已completed才能取原答覆。

### B4.2 cancellation、sweep、reset、stop

- `ct`只影響尚未取得admission gate的waiter及明確未接受階段。已開始可能寫入的admission不隨RN Ask timeout取消；先完成／確認durable結果，再回報。已接受innerTask不因caller停止等候而被取消。
- native turn使用既有TurnTimeout／wrapper cancel政策，不能把LINE十秒觀察時間變成native timeout。
- 一次只有一個sweep。保留Interlocked防重入，但用`currentSweep: Task`保存當次completion，DisposeAsync直接await；移除`while sweeping ... Task.Delay 10`。
- sweep選取entry只做短lock，實際await ReleaseAsync在lock外；新admission見Retiring仍遵原backpressure。
- ResetAsync／RecoverAsync／SelectAsync改為真正async Store API；與admission gate協調互斥，不能與新claim交錯覆蓋generation。reset標記後釋放gate再做remote close；其他admission依reset標記拒絕，不在gate內等模型。
- `DisposeAsync`是停止本地等待、清lease／lane，不等於關遠端native；`StopOwnedAsync`才對SQL記錄的owned WSID逐一close並確認。保留這個區分。
- explicit Stop順序固定為：BeginStop拒絕新admission→取得並釋放admission gate，確定先前進入者已完成reservation→快照SQL owned WSID與inFlight→向Fodex close所有owned wrapper，讓Fodex中斷native並確認清理→await本地工作settle及currentSweep→釋放本地lease/lane→完成runtime-close SQL記錄。**不能先等整輪模型自然結束才發close**，否則Stop又變成長時間等待。所有步驟共享caller提供的stop budget；任一close失敗則保留SQL RuntimeOwner/WSID與可重試控制路徑，不發布closed receipt。部分成功的wrapper可記錄完成，但不能把整批標成功。
- close/reset失敗保留原WSID/Generation供重試；不以建立新WSID消除錯誤。
- SQL synchronous constructor移除後，Service接收已InitializeAsync的Store（新增constructor必要參數），不要每個Service重做DDL。tests同樣先初始化。

## B5. `line_provider_fodex_v3_line.fsx`：不阻塞actor、不等整輪

### B5.1 prepare API

- `productionAdmission`改名`productionAdmissionAsync`，回Task，移除約197行的GetAwaiter().GetResult。
- `businessIdentity`改`businessIdentityAsync`：RouteIdentityAsync／SelectedAsync；不能只把reader await之後又同步查DB。
- `Adapter.PrepareAsync`仍同一次normalized read／parse，生成input與延後執行work；讀取raw的buffer在既有finally ZeroMemory。不引入會遮蔽變更payload的全域route cache。
- `responder`、lifecycle callback中的Store.Selected、Select、Mappings等全部await對應Async方法；不要只修入口兩行。

### B5.2 IngressActor精確receive模型

constructor的prepare參數固定改為：

```fsharp
fCell2<string> -> CancellationToken ->
    Task<Ingress * (RemoteWrapper -> Task<TurnReply>)>
```

使用ReceiveAsync。**只await prepare和durable admission，不在ReceiveAsync等待native turn**：

1. receive內立刻擷取sender/self以及該actor的logger。
2. 建立`TaskCompletionSource<string>(RunContinuationsAsynchronously)`作此次Ask的work觀察來源；立即啟動一次observer，以總觀察時間10秒計時（不是prepare後才開始計時）。
3. 在receive async task內await prepare；await service.SubmitWithAsync取得innerTask。
4. 另啟動輕量async continuation，將innerTask結果／錯誤轉給TCS；receive返回，下一個cell可開始prepare/admission。
5. prepare/admission失敗也傳到同一TCS；不用另一條reply邏輯。
6. observer使用WhenAny(TCS.Task, observation delay)：完成則回fCell2.S／Status.Failure；未完成則只回一次`v3-route-pending`。之後即使work完成也不再tell舊Ask actor。

因此十秒內即使metadata暫卡住，RN也可收到pending；accepted work繼續，redelivery仍經route dedup。不要用catch TimeoutException判斷pending，因native真正timeout也可能是此型別。

ReceiveAsync在prepare/admission期間會暫停該actor處理下一筆mailbox，**但會釋放dispatcher worker**。這是為保持目前入口接收順序；不新增ticket-reorder actor。當admission完成就解除，不把整個生成串行化。

actor內使用IInternalActor.ActorContext取得logger/context，避免FS0491；所有context存取在receive起始段，不於任意background continuation取Sender。

### B5.3 host與副本

- runHost先await Store.InitializeAsync再建立service／IngressActor，準備完成才宣告registration ready。
- 現有同步runHost入口可以在最外層main thread等待其async host task；不是actor內GetResult，不能把所有GetResult一律機械刪掉。
- 原RN cluster bootstrap、provider readiness、domain/image endpoints維持；Fodex service是另一個程序的ActorSystem，不join RN cluster。
- library-only副本必須不自動啟動額外node。正式runHost只建立原有RN node一次。
- lifecycle/test_mode/shared_bootstrap/shared_restore的argv/defaults注入與還原保持成對；測試新副本載入後原argv bytes/value未變。
- `line_provider_fodex_v3_transport.fsx`保持只對既有service送JSON；receive結果以AgentEnd與原request/cursor關聯判斷完成，不以第一個MessageCompleted判整輪完成。
