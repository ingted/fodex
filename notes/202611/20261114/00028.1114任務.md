## 2. 對外命令的精確語意

### 2.1 名稱、SID 與 Topic

- LINE 指令中的 SID 一律指 **root wrapper WSID**，不接受直接拿 Codex／AGY native SID 當 root。
- 完整 GUID 精確匹配優先；若輸入是 6～32 個十六進位字元，可作目前對話內 WSID 無連字號前綴，只有唯一匹配才接受。零筆／多筆均明確回覆，不猜第一筆。
- Topic 顯示保留原字串；比較採 Trim→Unicode Form C→ToUpperInvariant。限制 1～128 字元、不含換行、控制字元、`[`／`]`；不得是可解讀為上述 SID 的純 GUID／hex 前綴，以免 lookup 歧義。
- Topic 可含中文與空白；命令中含空白時加引號。SQL 存正規化 TopicKey 並以 binary collation 比較，不依 SQL instance 預設 collation 猜大小寫。
- 名冊、SID lookup 與前綴 lookup 都先用 account/sourceType/externalId 圈定；禁止跨對話找同名 root。
- 普通 `**[Topic] body` 是**這次指定目標**，不改預設 selection。保留 `**setagent <sid|Topic>` 作明確切換，修正現有 v3 被舊 whitelist 拒絕的問題。

### 2.2 `**newagent <agy|codex> <Topic>`

1. Argu 解析及 provider／Topic 驗證，不送模型。
2. SQL transaction 保留 Topic、配置新 WSID、保存完整 per-root argv 與建立 routeId，狀態 Provisioning。
3. 透過既有 Fodex service `create`，指定剛保留的 WSID。main native provider 取命令；subagent 預設仍 codex。選 Codex 時不可殘留 AGY model／adapter 預設。
4. 確認 service 回傳相同 WSID 且 root wrapper 可操作，才標 Ready；native 可維持 lazy，**不需要發問候 prompt／讀 AGENTS.md 來證明建立**。
5. 回覆 `Topic=<原名> SID=<完整WSID>`。原先 selected root 不變。
6. 同 routeId 重送回同一結果；同 Topic 的兩個不同 new 同時到達只能一個成功。建立失敗／timeout 不另生 WSID。
7. timeout 後用原 WSID attach／查狀態；若結果未知則保留 Provisioning，回可查狀態。清理已確認完成才釋放 Topic，不能把未知 ownership 當作沒有建立。
8. 舊裸 `**newagent` 回新語法使用說明，不再隨機建名或自動切換。

驗收差異：`create` 成功不等於 model turn 成功；newagent 的 Ready 表示 root／native binding 可用，native SID 在第一次生成前可尚未有值。列出的 SID 仍是 WSID。

### 2.3 `**listagent`、`**dropagent <sid|Topic>`

list 以建立序號穩定排序，每列至少 `Topic=xxx SID=<WSID前6碼>`；有相同前六碼時仍照格式顯示，附「前綴重複，請用 Topic 或完整 SID」。Provisioning／Dropping／Failed 項目須標狀態，不能顯示 ready。Dropped 不列入可用清單。

drop 是明確 destructive lifecycle 操作：停止該 root 及其 owned participants，再移出可選名冊；**不刪 SQL ReActEvent 歷史、native session 歷史、cache**。流程固定：

```text
resolve → 名冊標 Dropping／拒絕新 ingress
        → 取消該 root 尚未 seal/send 的 batch
        → service close 原 WSID，等待 owned resources cleanup 結果
        → 成功後 SQL tombstone + selection 修正 + Topic 唯一索引釋放
```

- close 失敗／未知：保持 Dropping，可重試同一 WSID；不得先刪 mapping 再留下 orphan。
- 已送出的工作由 close 中斷；晚到結果不能投給後來重用同 Topic 的新 root。
- 若刪 selected，回到對話的預設 main（存在且未 drop 時）；否則清 selection，下一個普通 prompt 才 lazy 建預設 root。
- Topic 可在 drop **完成後**重用，重建必須新 WSID。歷史 alias 不得解析到新 root。
- 刪的是 LINE root；不要翻譯成 `/remove(N)` 去移除另一張 graph 的某個 subagent。

### 2.4 解析層

新增 `line_provider_fodex_v3_commands.fsx`，定義簡單 DU + FAkka.Argu template。`**`／`**[...]` 是 transport normalization，參數解析用 ParseLine→Argu；禁止新手刻 key-value parser。優先匹配 `**model list`，再匹配 model set。

命令、reply formatting、Topic lookup 不經模型。只改 v3 copy，不修改／重新 #load 原 almighty 檔。先讀 `#load` 順序，避免 definitions 在使用後才出現。

## 3. 自動合併文字與圖片：持久化在前、送模型一次

### 3.1 分組與時間

分組 key：`(ConversationRef, resolved WSID, mapping generation)`。每個 item 保存原 routeId、LINE message id、sender、receivedAt、原 sequence、payload hash。到達新 item 時：

```text
dueAt = min(firstAcceptedAt + 10 seconds, lastAcceptedAt + 3 seconds)
```

先完成權威 LINE event 讀取與驗證，再把訊息存成 Buffered。延遲從 durable accepted 的時間算，不用可能倒退的外部訊息 timestamp 排序。SQL Sequence 是 batch 內穩定順序；重送同 route 不延後 timer、不增加 item。

文字先到、圖在 3 秒內到：只產生一筆 batch prompt（含文字與圖），不得先讓模型抱怨沒圖。圖→文字→圖同理。超過安靜期才來的圖片是下一批，不能宣稱任意時間都會合併。

明確 `**[Topic] 請看圖` 後，無文字 target 的圖片需要路由規則：同一 sender 在該 conversation 若有未 seal 的明確目標 batch，後續圖沿用該 batch 的 WSID，期限跟 batch；否則取持久化 selection。此暫時關聯不修改 selection，其他 sender 不繼承他的明確 target。多個候選時取該 sender 最後一筆已 accepted 的明確 target；重送不重排此順序。

### 3.2 控制與 batch 邊界

- 普通文字、明確 target 文字、圖片進 auto batch；new/list/drop/cache/model/setagent、`/next` 不進 auto batch。
- 控制命令與目前對話 admission 順序一致，但不等待該對話模型 generation 完成。必須避免舊 `tails[ConversationRef]` 把 list/cache/model 卡在幾分鐘生成之後。
- setagent 改變後續預設 target；已接納 batch 保留原 WSID。drop 取消目標未送 batch；model 暫停該 target 派送，batch 保留，參數變更後再送。
- 舊手動 batch 若使用者已開啟，由手動 finish 決定送出，不再套第二層 auto timer。未開手動 batch 的普通訊息才使用本功能；不能為測試成功暗中移除手動模式。
- 使用既有 actor scheduler／單一會話 coordinator，timer message 帶 BatchId+generation；過期 timer 忽略。禁止每 item 用 busy loop、Thread.Sleep、模型輪詢或新 ActorSystem。

### 3.3 SQL 與恢復設計

在既有 v3 store 擴充 `LineFodexV3Batches`、`LineFodexV3BatchItems`，延用 Routes 去重。這是 LINE durable ingress 資料，不放到 Contract。

| 表 | 最少欄位／約束 |
|---|---|
| Batches | BatchId PK、ConversationHash、SessionKey、WrapperId、Generation、FirstAtUtc、LastAtUtc、DueAtUtc、State、Owner、SendRequestId、ReplyRouteId、PreparedPrompt／hash、Result／error、UpdatedAtUtc |
| BatchItems | RouteId UNIQUE、BatchId FK、Sequence、CanonicalPayload／hash、MessageId、sender、media reference；索引 BatchId+Sequence |
| Routes | 仍保留每個 route 的 payload hash、reply／status；新增 buffered／batched 分支時修正 Lookup reconciliation，不能把所有非 completed 都當 indeterminate |

狀態：Collecting→Sealed→Sending→Completed；另有 Cancelled／Indeterminate。Seal 在 SQL transaction 固定 item 集合、ReplyRouteId、SendRequestId；seal 後到達的新 item 進下一個 batch。`SendRequestId = BatchId`，同一批永遠不換。

一次 `SubmitBatchAsync` 對全部 member routes 做一致性檢查，單次 RemoteWrapper.Request，模型結果寫回後：最後 accepted 的 member route 為唯一回覆承載者，其他 member routes 回既有 `Ignore` disposition，**不回空白文字、不 echo 圖片**。所有 member 的完成狀態／batch result／output cursor 必須同交易提交。

IngressActor 的 RN Ask observation window 現為10秒，不能把 Task.Delay(10s)+generation 塞進 ReceiveAsync。既有「durably accepted、RN pending/retry」模式仍有效；batch 管理 actor 能持續接收其他 route。最終由 RN 原有 reply token 流程回覆，沒有 LINE Push。reply token 失效／本輪沒能回覆時，結果留 SQL，下一個 `/next` 可取。

Crash 恢復：

- Collecting：從 SQL items 與 dueAt 重建 timer；到期立刻 seal，只做一次。
- Sealed 尚未送：使用原 BatchId 送件。
- Sending／ACK unknown：先依原 WSID+requestId receive／查既有工作；不能生成新 requestId 重送。只有服務能明確證明未 accepted 才可用同 id 再送。
- Completed：member route 重送直接回原 Reply／Ignore，不重新下載圖片或叫模型。
- 萬一批次資料 hash 不同、WSID/generation 已失效，拒絕並留可診斷狀態，不能改派現在 selected 的 root。

### 3.4 圖片資料與附件壽命

重用 `batchParticipantRequest` 的 `line-conversation-batch` 格式及 `images.imageUrls` 對 batch 的解析。先把所有圖完成下載／驗證，再生成一次 prompt；metadata 保留各 item 對 localImagePaths 的對應，不能只把 URL 串文字。

附件必須有 Fodex 可恢復的來源：將已驗證 bytes 交由 Fodex service 的 content-addressed asset operation 保存至 service 管理的 artifact root（SHA-256、長度、media type，檔名由 server 決定），取得 assetId 與正式可讀 path；同機本次可用現有 local route 檔作 transport，service 必須在接受 prompt 前複製完成。v3 清理只能刪自己的下載暫存，不得刪 service-owned asset。service 接收時驗路徑在允許的 v3 image root／hash，不接受任意 client 檔案路徑。

圖檔 reference 進 business prompt/FGL；原始 bytes 不塞每條 event。provider handover V401 的附件複製改解析 durable reference，舊路徑存在時仍可讀，缺檔仍明確失敗。本輪正式 LINE RN 與 Fodex 都在同機，因此 asset operation 僅實作受限本機匯入；遠端來源路徑回 UnsupportedRemoteAsset，不能把 client C:/ 路徑當成 remote 檔案。跨主機上傳協定不在本輪新增，亦不得宣稱跨主機圖片已支援。

限制要有限且可設定：沿用既有下載大小上限與圖片格式驗證；新 batch item 上限32、文字總量256KiB，達上限封存當前批後開下一批；單 item 超上限明確拒絕，不截斷內容。圖片下載失敗時回本批失敗，不能把不完整文字先送模型。

## 4. Topic 名冊與 root lifecycle 的 SQL／程式設計

擴充既有 `LineFodexV3Sessions`，保留原 KeyHash／Target／WrapperId，不把 Topic 直接當不變 SessionKey：

- 新增 ConversationHash、TopicDisplay、TopicKey、Provider、ArgumentsJson、Lifecycle、CreatedRouteId、CreatedAtUtc、DeletedAtUtc。
- 使用 filtered UNIQUE `(ConversationHash,TopicKey)` WHERE DeletedAtUtc IS NULL AND TopicKey IS NOT NULL。Provisioning／Dropping 仍佔名稱，drop 完成才釋放。
- Lifecycle 與既有 lease `State=idle/active/quarantined` 分欄；不可用 business lifecycle 蓋掉 owner fence。
- 既有 Target 保持穩定：新 root 用 `v3.agent.<creationRouteId>`；顯示與查找走 Topic 欄位。新同 Topic 不重用舊 Target。
- 遷移：main 對應 Topic `main`；其他舊 mapping 以 `legacy-<完整WSID>` 補名。舊 provider 從 Fodex typed binding／持久化 args 查證；無證據標 MigrationAmbiguous，不從 SID 格式猜 AGY/Codex，不用預設 AGY 偷改。
- Args 保存 Argu 產生的 argv JSON，不存命令字串拼接。Provider/adapter/model/effort 對每個 root 獨立；重啟透過此資料 Create 同 WSID。

把 `Client.Create(sid,ct)` 改為支援 `Create(sid,arguments,ct)`，保留舊多載作 defaults adapter 並註明用途。Service 的 factory 改接受 Mapping 取得 persisted args；同 WSID 若已有 live root，只能 attach，不以新 defaults 改 provider。

增加 Service 的控制 admission：route hash／owner／result 去重仍用既有 store，但 list/new/drop/cache/model 不先 materialize selected root。將 control work 與 generation tail 分開；只使用原短鎖與 await SQL，不能新增 lock 包 SQL／GetResult。

control gate只序列化接納與狀態轉移，不得持有它等待native停止或service Close，否則drop/model會與生成完成回寫互鎖。先把相應狀態/operationId提交並釋放admission，非同步完成後帶原WSID/generation回owner，再確認及提交結果。跨provider restart、model與drop共用同participant ownership gate；收到Busy回明確結果，不另開平行管理流程。

## 5. Fodex 共用 cache：一份 authority，FGL 與 KV 同步

### 5.1 對外語意

```text
**cache c key value   // create：存在則回 Conflict，不覆寫
**cache u key value   // update：不存在回 NotFound
**cache d key         // delete：存在刪除；不存在回 NotFound
**cache r key         // read：原文字／NotFound
```

需求原文的 d 帶 value 不作必要參數；有多餘 value 時回使用說明，不能忽略造成誤刪。value 為文字，可含空白、中文、多行；有空白建議引號，quoted value 保留原內容。key 用 Ordinal、大小寫有別、1～256字元、禁止 NUL；value 最大1MiB UTF-8，超出拒絕不截斷。沒有 TTL、自動 eviction、模型記憶摘要或 embedding。

共享 scope 固定為同一 Fodex cache service 的 StorageId：LINE bot、同服務的所有 root／nested／raw／COT 共同讀寫；**不依 Topic、provider 或 native SID 分庫**。所以不同 LINE conversation 的同 key 也共用，這是此需求的共享功能，不是 Topic 隔離規則。

### 5.2 選定架構

```text
LINE **cache ── Akka service cache request ─┐
native MCP cache_* ── cache MCP adapter ──┼→ ReActLoop.SharedCache
本機／遠端 IAgent wrapper control ────────┘       → 唯一 cache owner loop
                                                 → SQL transaction(event + KV)
                                                 → committed FGL projection → reply
```

使用一個**不帶 native／wrapper 的 control ReActLoop**管理 cache graph，service startup 建立一次。它採固定 StorageId 作 journal session namespace，Address 使用固定空字串，不依動態 Akka address 變動；namespace 與普通 wrapper WSID 分開，不能污染 `list_wrappers`／`list_participant` 的 N。

這是全服務 cache 事件的唯一 FGL，不在每個 root 複製一份可寫 cache graph；普通 wrapper 的 ReActLoop member 轉交 owner。透過既有 ReActLoop handler writer、store transaction、checkpoint codec 擴充，不另外引入 Akka.Persistence journal 或新 runtime 容器。

StorageId 固定為本輪保留的 cache namespace GUID `cace0000-1114-4000-8000-000000000001`；它在不同資料庫自然隔離，同資料庫所有service必須使用同值。一般 create_wrapper／--session 明確拒絕此保留SID；不用啟動時間或新的Guid.NewGuid產生cache scope。所有連入client不可指定另一個scope；cache endpoint health回StorageId與非機密storage識別，連線前核對。

### 5.3 Contract 草稿，需先 review

以下是介面語意草稿；實作時按既有宣告順序加入，不能直接把 UI／SQL type 放 Contract。

```fsharp
type SharedCacheCommand =
    | Create of key:string * value:string
    | Read of key:string
    | Update of key:string * value:string
    | Delete of key:string

type SharedCacheMutation =
    | Created of key:string * value:string
    | Updated of key:string * value:string
    | Deleted of key:string

// ReActEndpoint 加 SharedCache of storageId:Guid
// ReActNode 加 SharedCache of values:Map<string,string * int64>
// ReActEvent 加 SharedCacheChanged of streamId * operationId:Guid * mutation
// edge 固定 SharedCache(storageId) → 自己；revision 使用該 cache journal StreamId。

abstract member SharedCache:
    FeasibleT<Guid * SharedCacheCommand,
              Task<Result<string option * int64, exn>>, exn>
// read 回 Some value + 版本；mutation 回目前值/None + committed revision。
// 外層 Result 是同步參數／binding 錯誤，內層 Result 是非同步操作結果。
```

DU 名稱與現有 case 同名時由 type annotation 解決；不要新增 RequireQualifiedAccess，亦不加入 private/internal。`SharedCacheChanged` 是 control event，不是 AgentWork／AgentCot／HumanInit，不派送模型、不完成 turn、不加入 handover／compact 摘要。

拒絕 caller 用普通 RouteReActDataStream 注入 SharedCacheChanged；只有 cache owner 的命令流程能產生並 commit。Contract 只描述語意，unique writer／SQL／port／HTTP 留在 implementation。

### 5.4 SQL authority 與 crash recovery

新增獨立 KV 表 `dbo.FodexSharedCache`：StorageId、Key（BIN2）、Value nullable、Revision、IsDeleted、UpdatedAtUtc；PK(StorageId,Key)。Delete 使用 tombstone 保留 revision，read 當不存在。不要把 arbitrary cache 直接放 VersionRegistry.BaseCD。

事件沿用 `FodexReActEvent`，cache journal 使用自己 scope；為 mutation 的 operationId 增加可索引 nullable 欄位與 unique filtered index（scope/address/operationId）。append event、c/u/d precondition、KV 更新、idempotency 核對在**同一 SQL transaction**。同 id 同 payload 重試回原 committed result；同 id 不同 payload 拒絕。未接受的 Conflict／NotFound 不產生成功事件。

只有 SQL commit 後更新記憶體 FGL、回成功。commit unknown 先按 operationId 查 journal，不用新的 id重送。多 node／多程序不能只靠各自 mailbox 當唯一 writer；cache owner 以既有 SQL ownership／app lock 模式取得 scope lease，接手時恢復 graph 及 revision，再處理請求。失去 lease 立即拒寫，不自動形成第二個 owner。

恢復 cache 不套普通對話「最後一小時」視窗：load完整 cache checkpoint+其後所有 cache events；無 checkpoint 時從最初事件 replay。KV 表可作快讀投影，不能取代可 replay 的 journal。KV缺失／revision不一致時暫停 cache mutations，從 journal 重建該 scope 的 KV 與 graph，成功後原子換入；其他 LINE/model 業務可繼續。

刪 cache key、drop root、wrapper_compact、provider restart 都不刪 cache journal。Cache 自己的 checkpoint 保存全量有效值與 tombstone/watermark；一般 graph prune 不得碰這個 scope。

### 5.5 cache MCP 與註冊

新增只暴露 `cache_create(key,value)`、`cache_read(key)`、`cache_update(key,value)`、`cache_delete(key)` 的獨立 cache MCP host。Tools 只呼叫 ReActLoop.SharedCache；不直接 SQL／不在 tool class 保存另一個 Dictionary。mutation tool 支援 optional operationId，LINE用routeId，沒有帶的MCP呼叫由host建立並回傳；網路重試須沿用原id。

固定 endpoint 預設 `http://127.0.0.1:18825/mcp`，另加 `--cacheport`／`--cache-url` 的 Argu 參數。既有 service MCP 的 --mcpport 與 OrderHub URL 不挪用。supervisor／mcp 兩種 service mode 都可啟動 cache host；每個 service lifetime 一個，關閉順序為停止新cache寫入→drain SQL→停host→停owner。console 連既有 --cache-url，不因每個 CLI／wrapper 自建 cache service；無 endpoint 時如實顯示 unavailable，不能建一份隔離資料冒充共用。跨機participant必須收到它可達的配置URL，不能把owner的127.0.0.1送給另一台機器；遠端曝光沿既有有驗證的proxy，不在本輪另開無驗證公網listener。

AGY（本輪使用者已同意）：

```text
agy mcp add fodex_cache http://127.0.0.1:18825/mcp
```

本機 `agy mcp add --help` 已查到 name+URL、http/stdio、header/env，flags必須在name之前；全域help沒有每process的 --mcp-config。只在確認 scope/name/url 後冪等註冊一次、必要時 enable；若名稱已存在卻指別的 URL，明確報設定衝突，不悄悄overwrite。不得把模型生成當註冊檢查。管理命令也由 Proc Supervisor SOP 執行、保存exit狀態，不新增裸 Process.Start。

Codex：組合既有 mcp_servers dict，在保留使用者與order hub設定之下加 `fodex_cache`。app-server走 initialize/thread配置既有管線；exec走既有 -c config 展開。cache ready後才放行native第一個turn。raw目前沒有完整configuration input，必須補新版creator；handover candidate、resume、COT、nested main亦走同一composition。不要把 root 的生命周期hub tools順便授予所有 raw participant。

真實驗收需工具清單與一次實際cache呼叫；只有ARGV含URL、HTTP health成功或模型自稱有工具均不算。

## 7. `**model` 與動態模型清單

### 7.1 `**model <sid|Topic> <model> <effort>`

Target經第2節resolver取得root WSID；再由Fodex graph沿Main關係找到真正leaf native。不能寫死N=2，nested main也走同一個解析。以typed `NativeAgentSessionId(provider,sid)`／持久化args查provider；有不一致直接報錯，不憑model名稱前綴判provider。

處理順序：

1. 取得該provider的動態catalog成功快照，驗證model與effort的組合。
2. model不在該provider目錄時，LINE回：`指定的模型錯誤，該 native 為 agy` 或 `指定的模型錯誤，該 native 為 codex`。需求文字中的code統一採既有canonical provider codex。AGY本身可能也提供GPT模型，不能看到gpt字樣就判Codex。
3. catalog查詢失敗要回「模型清單暫時無法取得」，不能當成不支援，也不能先cancel。
4. model+effort是一組原子change；驗證通過才取得該participant control gate。若正在生成，先cancel並等這次run停止，再一次套用兩個參數；若idle就只改下一次turn設定。
5. 更新native設定、持久化effective args與graph metadata；成功ack後才釋放buffered prompt。只送一個「接續既有工作」continuation，沿用現有V408的副作用去重提醒，不重放整份LINE batch。idle時不生成測試問候。
6. 套用失敗保留原設定／明確回報目前是否已中斷；不誤報成功，不自動換provider或fresh SID。

WSID、N、native SID、provider、generation維持。若某provider實際不能在原session套新model，回Unsupported並保持原binding；不能偷用RestartParticipant處理。本機AGY每輪argv已可帶model/effort，Codex exec亦如此；app-server按既有turn參數設定，不重啟全service。

加入最小的ReActLoop typed operation（Contract review項目）：

```fsharp
abstract member SetNativeModel:
    FeasibleT<ReActParticipant * string * string,
              Task<Result<ReActParticipantInfo, exn>>, exn>
// input = participant, model, effort；owner處理完整 validate/cancel/apply/persist。
```

Line用service protocol `set_model` 轉到root loop；MCP可新增同一operation的薄工具（外部service MCP，不擅自把root修改權加到所有sub）。原 `/model`、`/effort` 也應在新版共享同一provider-aware validation，避免LINE通過而CLI仍拿Codex目錄驗AGY。

### 7.2 `**model list <agy|codex>`

Fodex提供 `NativeModels.List(provider, forceRefresh)` 的FodexFun；LINE只格式化回覆。**官方當前支援**在產品中精確定義為「本機已登入的該provider CLI／服務目前回傳、此帳戶可用的目錄」，不是網頁全產品名單、訓練記憶、或硬編碼enum。

- Codex：沿 `NativeModelCatalogFodexFunV301` 的 app-server initialize→model/list分頁，正確處理nextCursor、重複cursor、空結果。只查目錄、不建立thread或生成；暫時process由Proc Supervisor清理。顯示可用非hidden模型，保留raw metadata供判斷；明確隱藏／不可選的項目不可當一般可選model。
- AGY：沿本機 `agy models` 動態輸出；`agy models --help`目前只提供help，沒有JSON flag，不能虛構 `--json`。使用新版parser處理tab欄位與提示行，查詢exit失敗／空結果回Error，移除V300硬寫模型fallback。model名串入JSON須用JsonSerializer，不用sprintf未escape字串。
- AGY的現行V300把每個model都宣告high/medium/low，這不是後端證據。新版只標實際取得能力；沒有逐model資訊時顯示「CLI effort選項，model個別能力未宣告」，沿已查證的CLI選項及high/low preset互斥規則驗證，不把猜測寫成官方catalog。
- 顯示provider、fetchedAt、資料來源、model id及可取得的effort／預設資訊。長列表分頁留在LINE deterministic output queue，由 `/next` 領取，不能丟模型摘要。
- 正常validation可用5分鐘cache；顯式 `**model list` 要刷新（同provider同時多請求合併一個in-flight query）。失敗可顯示上一份快照但必標stale與時間，不能拿stale清單批准新model設定。既有正在生成的工作不因刷新失敗被cancel。
- cache key含provider、executable identity、帳戶／工作設定scope；不要將不同provider目錄共用同一models array。此catalog cache是內部效能資料，**不是使用者 `**cache` 的文字KV**。
