日期：2026-11-19。狀態：**設計交付，尚未實作 v4**。本文件取代「再把 CLI process 接到 Provider」的方向；既有 v3 與獨立 Fodex CLI 保留。

**摘要**：新增正式 `Fodex.Line.V4.exe`，一個 foreground process、一個加入既有 RN cluster 的 ActorSystem，內含 LINE Provider endpoint、Fodex service supervisor 與 Console。每個 LINE conversation 有自己的持久化 wrapper 名冊／目前選取／預設；Console 操作目前聚焦 conversation 所選取的 wrapper。LINE 與 Console 都經既有 service bridge → `IAgent.Request`／`IAgent.Send` → ReActLoop，實際 native session 共用，不建立第二個 CLI main。PTC 仍只綁定 account 的 Provider actor，不處理 Topic、SID 或 Fodex 命令。CLI 的 prompt 與完整回答可由 `/next` 或下一次正常 LINE 回覆領取；raw stdout/stderr 維持獨立。

## SECTION 1 — PTC LINE 專案：保留 account 綁定與正式歷史投影

### 1.1 已確認的行為與需要更正的認知

1. 管理介面的 Generator 設定以 LINE **account** 綁定 Provider actor address。v4 不再實作一套 account 搶占／路由服務。兩個 instance 不可同時占用相同 node port；不同 instance 使用不同 port，且管理介面須綁到實際 instance 的 endpoint。
2. Provider 內部的 conversation key 已經是 `account + sourceType + sourceId`：一對一採 userId、group 採 groupId、room 採 roomId。**group 內不同 sender 不拆成不同 conversation，也不因顯示名稱相同而跨 group 合併。**
3. PTC LINE tab 的 conversation 是 LINE 訊息歷史範圍，並非 LLM SID。LLM 連續性來自 Provider 持久化的 conversation → selected/default wrapper → native SID 對應；不是 UI 幫忙保存模型記憶。
4. 因此「同一個 LLM session 通到底」的精確意思是：同一 conversation、同一個選定 wrapper，在沒有 restart／compact handover／agent-type 切換時，持續 resume 同一 native SID。`**newagent`、`**setagent` 仍能在同一 group 選用不同 wrapper；不得為了 v4 把一個 group 限縮成永遠只有一個 agent。
5. 現有 v3 依事件 `source.userId` 與 `allowedLineReplyUserId` 比較，只讓授權 sender（目前 NorthPole）進入模型。**不是先查群組成員名單。**沒有 NorthPole 發言的群組自然沒有獲准的模型輸入。
6. 現況並非完全 silent drop：legacy 路徑有固定未授權答覆；Ordered admission 的 `AdmissionRejected` 會產生 `ResultDisposition.Reply` 的拒絕文字。v4 要修成 **非授權 sender → `Ignore` → 不回 LINE**。這個修正在 Provider，不是移除 PTC inbound 歷史或改 LINE tab。
7. 授權必須比對部署設定中的穩定 LINE userId；NorthPole 只是人類辨識用名稱。現有來源是 `allowedLineReplyUserId`，不是已存在的 PTCS「允許顯示名稱」設定。v4 將這個既有值沿用為部署設定，不新增 PTC UI 欄位；不得接受同名其他使用者，也不得從 user prompt、CLI 輸入或模型輸出取得授權身分。

### 1.3 account、conversation、wrapper、native 的區別

```text
PTC 管理設定：d9System_test2 → v4 Provider actor address
  conversation A（account + group + groupId-A）
    Topic=main → WSID-A → main native SID-A
    Topic=review → WSID-B → main native SID-B
    selected=B，default=A
  conversation B（account + group + groupId-B）
    Topic=main → WSID-C → main native SID-C
    selected=C，default=C
```

- `Topic=main` 可出現在不同 group；WSID／native SID 不可因此共用。
- Provider root 表現有 WrapperId 唯一約束繼續保留。同一 root 不同時屬於兩個 LINE conversation。
- PTC 數字 conversation ID 只用於管理查詢／CLI 選取；進資料層後仍採目前 authoritative account/source key 與既有 canonical/hash 函數，不重新發明 hash。
- `**[Topic]`／`**[SID]` 僅解析目前 LINE conversation 的名冊，知道別群 SID 不等於能使用它。
- v4 的 CLI 是本機人類介面，使用它選定的 conversation；本機輸入沒有 LINE senderId，也不偽造 NorthPole。

### 1.4 正式歷史流程與 CLI transcript 的呈現

```text
真 LINE 訊息 → PTC inbound history → Ordered Provider
                                  → v4 wrapper
wrapper 完整回答／待領 CLI transcript
  → Provider 保存 immutable LINE messages page
  → RN 以真 carrier／reply token 發送
  → Accepted → 既有 conversation projection → PTCS LINE tab
```

例如 CLI 輸入 `請檢查 A`，產生 `A 沒有異常`，之後 LINE `/next` 取得：

```text
[CLI 對話 · Topic=review]
使用者：請檢查 A
Agent：A 沒有異常
```

上面整段是 **official account 的一則或多則 outbound message**；不拆出假的 NorthPole inbound，也不給 CLI prompt 虛構 LINE MessageId。PTCS 只在實際 LINE outbound 被 Accepted 後顯示這段。尚未送到 LINE 的 CLI 對話保存在 Fodex／Provider，**本輪不增加 PTCS 的未送出 CLI 專用 UI**。

11/18–11/19 歷史修復已做：從保存的 Accepted result 重建訊息、驗證 route／attempt／digest、outbound idempotent 補投影、晚補資料按事件時間插入、保留同步 cursor。v4 不再自建另一套歷史 writer，也不能用重新呼叫模型或重新送 LINE 來修歷史。補投影故障與 LINE 發送故障要分開：前者可重試投影，不能重送已 Accepted 的內容。

## SECTION 2 — LINE Provider：將 v3 能力編譯成 v4，並接上共用 CLI

### 2.1 正式產物與 process ownership

新增 **`F:/fodex/Fodex.Line.V4/Fodex.Line.V4.fsproj`**，assembly／executable 名稱 `Fodex.Line.V4`，net10.0，正式 application，不是 demo project。新增對應 `Fodex.Line.V4.Tests`，並加入現有 `Fodex.Supervisor.slnx`。ProjectReference 指向 `Fodex.Supervisor`；後者是 exe assembly 也不代表載入時會執行它的 entrypoint。v4 **不啟動另一個 `Fodex.Supervisor.exe`、FSI 或 PowerShell host**。

v4 process 擁有：

- 一個 RN-compatible ActorSystem、Provider ingress／worker、Fodex service supervisor、root wrappers 與其 native 子程序。
- 一份 Console input/editor、printer actors、焦點狀態；每個 wrapper 的獨立 native I/O subscription。
- 本 instance 建立的 cache／root hub listener；不關閉外部 PTCS、RN Host、GW 或其他 instance。

預設 node port `15979`；name 使用 RN cluster 要求的 `PulseTradeCommResourceNode`，不是隨意另取 `fodex-line` 加入既有 cluster。新 endpoint 固定 `/user/line-fodex-v4-ordered`。不同 instance 指定不同 port，既有管理設定再綁定該 instance。port 被使用時清楚失敗，不殺占用者，不偷偷挑另一個 port 讓管理 address 失效。可以提供 `0` 供隔離自動化動態配置，但必須輸出真正 bound address；一般部署用明確 port。

同機各 instance 的 data directory／cache listener port 也必須分開。AGY 的固定 `fodex_cache` registration 繼續遵守現有一致性檢查：若另一 instance 的同一 AGY config scope 已註冊不同 URL，不覆寫；使用既有相容 endpoint 或不同已配置 AGY profile。多 instance port 不同，不代表可以搶改共用 AGY 設定。

### 2.5 CLI 焦點：明訂 group 邊界，避免實作時猜

既有 selected/default 是 **每個 conversation 一份**。新增的 CLI focus 是「目前終端看哪一個 conversation」，不是把所有 group 的 selected 合成全域一筆。

新增 `dbo.LineFodexV4ConsoleFocus`：key 為配置穩定的 instance scope（account＋Provider storage scope），欄位 ConversationHash、Revision、UpdatedAtUtc；用既有 conversation 正規化與查詢確認 ownership。不要把 process PID 或每次隨機 runId 當持久化 key。selected root 仍從既有 `LineFodexV3Selections` 取得，不另存第二份 SelectedWrapperId。

開機依序：

1. 有 `--line-conversation`：從 PTC authoritative conversation lookup 確認屬於指定 account，再設定焦點。
2. 否則恢復該 instance 上次有效焦點。
3. 無焦點且僅有一個既有 conversation 名冊：選它。沒有或有多個候選時，顯示清單／待選狀態，不猜測「最新群組」或把 CLI 歷史事後送到第一個來訊 group。
4. 待選時可使用本地 `/line_context` 列出、`/line_context(<PTC conversation ID>)` 選擇；ArGu 解析，純本地路由控制。尚無任何有效 conversation 時，等待授權 LINE 首次來訊建立，或使用明確 conversation 參數。普通 CLI prompt 在未選定前明確拒收，**不啟模型、不暫存成可能跨群外洩的輸入**。
5. 首次授權 LINE 來訊可建立該 conversation 的預設 main；僅在 Console 尚未有焦點時設定為焦點。不同 group 的普通來訊不搶走既有焦點。
6. LINE `**setagent <sid|Topic>` 成功時，同 transaction 更新該 conversation selected 與 ConsoleFocus；commit 後通知 Console。這是人類明確的切換。跨 group 的 setagent 以成功交易的 focus Revision 排序。
7. CLI 的 `**setagent`／`**newagent`／`**setdefault`／`**dropagent`／`**whoami`／`**listagent` 使用相同 domain operation，scope 為目前焦點 conversation；不偽造 RN Header 或 LINE sender。`**setdefault` 只改預設，保留目前選取；default 仍不可直接 drop，即使 --force。

取得有效 conversation 後，若其 root 名冊確實為空，沿 `EnsureConversationRootsInTransactionAsync` 的既有序列化規則建立一組預設 main，讓 CLI 可立即操作；這是 logical wrapper 建立，不啟 native。CLI 與首次 LINE admission 競爭時仍只有一個 default。名冊有 MigrationAmbiguous／失效選取不等於空名冊，不能藉此新建替身掩蓋舊問題。

上述新增 `/line_context` 只解決多 group 的本機焦點，不改 LINE `**` 語法。prompt 的字面保持 `fdx.yymmddhhmmss> `；開機、切換焦點與來自非焦點 wrapper 的輸出另印 account／conversation／Topic／短 SID 標籤，避免誤認回覆來自當前 main。

每次 CLI submission 先凍結 `(conversation, WSID, mappingGeneration, selectionRevision)`，後續切換不改它的歸屬。舊 wrapper 的遲到輸出要印原 target 標籤，不更新 focus。reconnect 失敗、MigrationAmbiguous、default 缺失都要顯示具體原因；不可無聲新建 session 蓋掉舊資料。

### 2.6 兩條輸入路徑與保序邊界

```text
CLI readSubmission
  → Focus actor：取目前 conversation／selected snapshot
  → 保存 CLI operationId／目標／prompt
  → 本 node Service supervisor bridge（send）
  → IAgent.Request → wrapper actor → ReActLoop → main native

LINE raw event
  → RN 原有 durable admission／authoritative reader
  → sender 授權 → B transaction：凍結 target／batch
  → 原有 Ordered worker／materialize
  → 同 node、同 WSID 的 Service bridge（send）
  → IAgent.Request → 同 wrapper／main native
  → 收到受理 acknowledgment 後，通知 Console 印「LINE 輸入」
```

LINE worker 不調用 Console submit，不寫 Console.In，不讓顯示函數再次叫 Send。CLI 也不假造 LINE 原始事件進 PTC。圖文 batching 維持同 conversation＋同 target 3 秒安靜期／10 秒上限；CLI 已完成的一次多行 submission 不再套 LINE batching。

同一 wrapper 的 service bridge／actor 提供受理與狀態順序。不同 sender 的牆鐘先後、B admission 時間、圖文等候時間，不等於 wrapper mailbox 的全球順序；不要承諾跨來源絕對 FIFO。可驗證的是：每個已受理 operation 有唯一 ID／凍結 target，按 actor 實際受理順序處理，輸出能回到原 operation。

不得等 AgentEnd 才讓 actor 處理下一則控制命令。長 SQL／model await 用既有 async／completion message 模式；Console 讀取與 `/cancel`、`/stop`、`/exit` 持續可用。普通 prompt 與 `/wrapper_immediate` 在 busy 時的 cancel/steer/queue 語意沿當前 wrapper 實作，不另加一個 CLI「等待整輪」鎖。

CLI 與 LINE 同時操作同 root 的 lifecycle 時，沿現有 root control lease/generation；不能在 CLI 繞過 default 保護直接 dispose。普通 prompt 經 service 的既有 journal；LINE worker 的 lease 不拿來阻塞本機取消。若取消令原 LINE work 結束，須完成原 work 的 cancelled/failed 結果並釋放 lease，不讓 ordered-root-owner-busy 永久留存。

### 2.7 非授權 sender 的 silent Ignore

在 `LineV4OrderedAdmission` 已驗證 binding、account、authoritative raw identity 之後，**解析命令／建立 root／更新 focus／物化圖片之前**判斷 sender。

新增小型 admission intent case，例如 `IgnoredSender of reason:string`，與現有業務錯誤 `AdmissionRejected` 分開。B transaction 保存 terminal receipt/output：`WorkOutcome.Succeeded`、`ResultDisposition.Ignore "sender-not-authorized"`、empty content、無 Root binding。沿既有 output digest／ReadyResult 格式；Ignore 不帶 InlineMessages。不排 worker、不留給 /next、不寫未授權 reply text。

未提供 userId 亦採同樣拒絕模型的政策；不以 group display name 代替。legacy 相容 endpoint 若仍部署，也回既有 `Provider.Ignore`，不能一條 silent、另一條仍 reply。v4 主線只註冊 Ordered generator；保留的 legacy helper 不主動宣告為另一個可接單 generator。

### 2.8 CLI transcript 的持久化與完整性

Fodex SQL／graph 是模型歷史來源；Provider 只保存跨 CLI／LINE 的關聯與交付狀態，不複製 raw event queue，不把 graph snapshot 當完整歷史。

新增兩張用途明確的表（名稱在 v4 固定）：

| 表 | 必要欄位與約束 |
|---|---|
| `LineFodexV4CliTurns` | OperationId uniqueidentifier PK；Account／ConversationHash／WrapperId／MappingGeneration／ReActSessionAddress；InputText、InputOrigin=`Cli`；CauseStreamId nullable；CompleteStreamId nullable；State（Prepared/Accepted/Completed/Failed/Indeterminate）；CreatedSequence identity、UTC。重試同 ID 必須驗 body/target 相同 |
| `LineFodexV4CliReplyItems` | `(OperationId, FragmentOrdinal)` PK；不可變完整對話片段、digest；ClaimedResultKey nullable；DeliverState（Pending/Claimed/Delivered/Unknown）；對應 output 的 offset/ordinal。不可用 console shown 代表 Delivered |

不是另做一套 model job engine：send/observe/close 的 authoritative 狀態仍是既有 service journal。CLI Prepared 後呼叫 service send，使用同 OperationId；失敗／timeout 先 observe 原 ID，不能生成新 ID 重送。只有 confirmed complete 的 root turn 產生可領取 transcript；尚在生成時 `/next` 不標記它已讀。

完整對話投影使用第 3 節 `Conversation.ReadCompleted`：依 WSID＋causedBy／AgentEnd 關聯取 Human prompt 與 root human-visible Message／MessageCompleted；相同 messageId 的 delta/completed 不重複。原始 CLI InputText 是顯示 prompt 的權威，SQL 保存的 typed graph edges 是驗證及回答來源。SQL session key 的 Address 必須沿實際 root session 保存，不能把 Some(IP) 自行改成 None 導致讀不到歷史。控制命令（show/list/cancel 等）不冒充 LLM 對話。錯誤／取消可輸出明確狀態，但不可把未完成字串當成功回答。

訂閱 output 必須在送件前完成，短回覆可能比 send ACK 先到。若收到 AgentEnd 時 Cause 尚未寫回 CliTurns，先依 OperationId 讀既有 journal，完成關聯後再落片段；不能漏掉或猜第一個 AgentEnd。具體使用已存在的 `Service.RequestStore=1.0.1`，input `(cs, WSID, operationId.ToString("N"), (ReadServiceOperation, None))`，驗證回傳 Wrapper/Id/Text/Generates，取得 `ServiceOperationV100.Cause`；Cause=0 不能當完成。普通 `send` ACK 不保證帶 cause，禁止假設 wire 已有那個欄位。此 read-only lookup 經 FodexFun，不在 Provider 手寫 FodexServiceOperationV1 SQL。後續 subagent 回灌引起的新 main turn，只在既有因果鏈可證明屬於該 CLI 操作時併入；不確定時保留原 SQL history，不能跨操作猜配。

產生正文時：

- 只要 wrapper → Human 的使用者可見內容；不暴露 subagent/COT 內部輸入、工具結果、native raw JSON。
- StdOut、StdErr、MessageDelta、`NativeOutputBatchV300` 一律排除。
- 優先完整 MessageCompleted／完整一般 Message；AgentEnd 作 turn 完成界線，若其 Message 是同一 final 文本則去重。
- 大對話依現有 Rune／LINE textPages 邊界分片，保留完整 prompt＋response，標示順序，不用 60KB handover 或 compact 上限截斷 LINE transcript。
- late output／重啟補掃採唯一鍵 idempotent。以待完成 CLI operation 的 cause 作 SQL 起點，不每次讀整個 graph。現有 CollectAfter 尚無 page-size 參數，不能假稱固定大小；不相關的舊歷史不讀，若一次長回合資料過大，保留進度與明確診斷，不截斷正文。

### 2.9 `/next` 與下一次 LINE 回覆：共用同一份 claim

本版同時支援兩種領取入口。它們領取的是 **目前 LINE conversation、target wrapper、mapping generation** 下的 CLI pending 片段；不因當前 Console focus 在另一群而改變 target。

**正常 LINE prompt**：B 先凍結 target，既有生成流程不變。在 C materialize reply 時，transaction 按 CreatedSequence／FragmentOrdinal 擷取可放入本頁的 CLI Pending，再加本次正常回答。內容凍結後寫既有 OrderedOutputs，保存每個 CLI fragment → OutputRef/ResultKey 的 claim。LINE 本次回答本身不得被 CLI 舊資料擠掉；至少保留本輪正常回答的第一頁，超量 CLI 維持 Pending，由 /next 領取。

**`/next`**：沿既有 query/rejection 優先及舊 LINE output 選取規則；沒有先前可領輸出時，為 Pending CLI fragments 用本次真正 `/next` receipt 建立 immutable output/page。已 Claim 到可領 output 的 CLI fragments，只重用該 output reference，不建立第二份。沒任何完整內容時回既有「目前沒有可領取的結果」。這條路不 Create/Send/Start native。

**關鍵協定邊界**：CLI 沒有 RN RequestRoute／reply token。不能偽造 Header、Receipt、ResultRef 發到 RN；CLI 的 pending 資料直到真 LINE carrier 進來才 materialize 成該 receipt 的合法 output。現有 LINE 舊 output 不重新包成另一份「已送出」結果；保持原 subject authority。CLI fragment 是本機內容來源，不是自行假造的 RN subject。

`LineV4OrderedStore.RecordOutcomeAsync` 在既有 outcome revision/identity 驗證通過的 transaction 內更新對應 CLI claim：

| 狀態／故障 | 行為 |
|---|---|
| Console 已顯示 | 不改 LINE pending/claim |
| Output 產生，尚無 Accepted | Claim 綁原 immutable output；不能再次挑進另一個 reply |
| RN subject 確認 Accepted／已完成交付 | 對應片段標 Delivered；不憑 Provider 自己猜 |
| token 過期／確定未送，可 AvailableForNext | 保留原 output，下一次 /next 沿 RN 正式續取 |
| Unknown | 維持原 output＋Unknown，沿現有 RN 人工／查證與續取規則；不自動重組重送，不宣稱 exactly-once LINE transport |
| crash 在 commit 前 | 無 claim；下次仍可 Pending |
| crash 在 output/claim commit 後 | 從同一份 output 恢復；不得再次生成模型回覆 |
| 重送相同 outcome revision/body | idempotent；同 revision 不同 body 按現有 conflict 失敗 |

claim、immutable bytes、output metadata 必須同 transaction 提交；不能先把 CLI 項目刪掉再呼叫 LINE。若已完成一部分分頁，只標已確認頁面的 fragments，其他保留。SQL 原始歷史不因領取而刪除。

### 2.10 跨 v3／v4 的持久化與退出

- v3 → v4 使用相同 Provider storage DB、conversation key、root WrapperId、generation、native identity 與已保存 arguments。不把新 `mainagent-type agy` 當成舊 Codex root 的 provider 證據。
- protocol `GeneratorProviderId`／`StorageIdentity` 是 durable authority，不等於 exe 版本。本版保留既有 `fodex-line-v3` durable provider ID 與實際 storage identity；新 actor path 可叫 v4。不能只換 provider ID 讓舊 `/next` output 全部變不可見。
- 管理設定的 address/revision 依正式流程更新；approved-bindings 顯式批准新 revision，必要的舊 outcome recovery revision 亦逐筆明列。不能由 incoming Header 自動學習 authority。
- 切換前停 v3 admission、drain／保留 pending work、確認 owner release，再啟 v4。不能兩個 executable 以同 owner/port 消費相同 durable work。未完成／Unknown 的原始 receipt、native operationId 保留，不當新 prompt 重播。
- 重啟 v4 恢復 focus／selected/default/root metadata；Create/attach 只恢復邏輯 wrapper，首次需要模型才 resume native。相同 provider 沿 SID resume；改 provider 必須用既有 graph handover → 新 SID 流程。
- `/exit`、Ctrl+C、Console EOF 共用一個 cancellation/lifetime path：停止新受理 → 停 Provider worker/reader admission → 等進行中的提交／outcome transaction 收尾 → service shutdown／wrappers cleanup confirmed → cache/listener 關閉 → node Terminate → printer drain → exit。
- 不等待 LLM 自然生成完才退出；沿現有 stop/force cleanup 預算。只有證據確認全部 owned child 結束才報 graceful success；超時報告精確 owned actor/PID+creation time，不掃殺全機 codex/agy。
- 退出不是 `**dropagent`：名冊、selection、SQL history、native SID 仍可恢復。終端關閉後 LINE 不繼續提供本 instance 的服務。
- 正常 Ctrl+C 的事件處理不得被 editor 無限攔截；平台允許的 console closing 使用同 lifetime。強制 kill/斷電無法保證 graceful，依現有 Proc Supervisor／Windows job 保護＋下次 owner recovery，不冒稱所有 OS 都有同一保證。
- 沿 `ProgramV416.fs` 已有的「第一次 Ctrl+C 取消、超過 shutdown 預算或第二次 Ctrl+C 結束自己的 process tree」外層保底；只能作用在本 v4 executable 的 own tree。不能把這個 forceExit 放進借用 node 的 library disposal，否則會誤殺宿主。

### 3.2 精確新增的 target、版本及型別

以下是**計畫新增**，不是宣稱現有 API。型別皆放各自 `.fsx` 的 module 前，F# 依序編譯。以 tuple／現有型別為主，僅使用解釋必要語意的小型 DU；不用 new Application、runtime class 或 FodexEntry。

| 新檔 | target / version | Input → Output |
|---|---|---|
| `ServiceObservedWrapperFodexFunV100.fsx` | `Service.CreateObservedWrapper` / 1.0.0 | `(ServiceWrapperCreationV100 * (Guid -> ReActDataStream<string> -> unit) * (Guid -> NativeOutputBatchV300 -> unit))` → `Task<Result<ServiceWrapperV107,exn>>` |
| `ServiceHostOnNodeFodexFunV100.fsx` | `Service.StartOnNode` / 1.0.0 | node、ctx、SQL、既有 Console options、cache URI、兩種 observer、CancellationToken → `Task<Result<(IActorRef * IAsyncDisposable),exn>>` |
| `ConsoleFrontendFodexFunV100.fsx` | `Console.RunFrontend` / 1.0.0 | node、ctx、options、TextReader、TextWriter、diagnostics、submit callback、CancellationToken → `Task<Result<int,exn>>` |
| `ConversationProjectionFodexFunV100.fsx` | `Conversation.ProjectCompleted` / 1.0.0 | `(ReActParticipantSessionId * StreamId option * ReActDataStream<string> array)` → completed turn array |
| 同上檔 | `Conversation.ReadCompleted` / 1.0.0 | `(FodexNode * string * ReActParticipantSessionId * StreamId * StreamId array)` → `Task<Result<completed turn array,exn>>`；string 為 SQL connection，StreamId 為完成水位，最後為尚未完成的 CLI causes |

completed turn 使用一個清楚的型別即可，例如 `(cause:StreamId * completedAt:StreamId * prompt:string option * messages:(string option * string) array)`；messageId 可缺省但不能因此拼接 delta。wrapper 身分由 input 決定；不在結果加入 LINE account／reply token。

ReadCompleted pin 既有 `ReActCheckpoint.CollectAfter=4.0.3` 與 `ReActCheckpoint.FindEvent=4.0.3`：從完成水位與未完成 causes 的最小必要起點讀取；對缺少的 causedBy 祖先用 FindEvent 補齊，偵測 cycle／缺失並報錯，最後依完成水位選完整 turn。沒有待查 cause 的空查詢直接回空，不為 /next 掃全歷史。不得只讀完成水位之後的 edges 而遺失該 turn 的早先 HumanInit／訊息；遇到同一因果鏈內較早已輸出的 MessageCompleted 也要保留後再去重。這是 Fodex 內的 SQL 讀取 composition，Provider 不寫 SQL event 解析器，也不需要取得／另存 live ReActLoop instance。

需要完整查詢的既有 ReActLoop caller 可將 CollectAsync 結果交給 ProjectCompleted；v4 的增量讀取走上面的 ReadCompleted。兩者共用同一個 pure projection，不能演化出兩份 delta/completed 判斷規則。

`Console.RunFrontend` 的 submit callback 定為 `string * CancellationToken -> Task<Result<string option,exn>>`，回傳 optional acknowledgment，不等模型完成。顯示端由既有 ConsolePrinter 建立 `post`；host 的 typed event observers 使用同一 printer 通道。為避免 frontend 與 host 同時各建一套 editor，frontend input 另外帶一個 `attachDisplay : (bool -> string -> unit) -> IDisposable`，frontend 建好 editor/printer 後呼叫一次；返回 subscription 在退出時 dispose。這是本機 composition callback，不是可 remoting／寫入 quotation DB 的捕獲物。

`Service.StartOnNode` 的 tuple 應明確宣告 alias，不要在每處重寫九個 unnamed 參數：

```fsharp
type ServiceOnNodeInputV100 =
    FodexNode * UniContext * string * ParseResults<ConsoleArgumentV405> * Uri *
    (Guid -> ReActDataStream<string> -> unit) *
    (Guid -> NativeOutputBatchV300 -> unit) * CancellationToken

type ConsoleFrontendInputV100 =
    FodexNode * UniContext * ParseResults<ConsoleArgumentV405> *
    TextReader * TextWriter * TextWriter *
    (string * CancellationToken -> Task<Result<string option, exn>>) *
    ((bool -> string -> unit) -> IDisposable) * CancellationToken
```

wrapper observer 與 native observer 保持兩個 callback，不能合成 ambiguous `obj` 或字串 channel。這些是實作 input aliases，不加入 Contract。

### 3.3 Service.CreateObservedWrapper 的實作細節

以 V108 為基底複製為新檔，保留以下內容：

- override argv allowlist、typed options parsing、現有 SQL registry 設定與 factory 4.1.3 pin。
- 每 root 的 URL／transport、FodexAgent object expression 與 CreateReActLoop/CreateWrapper。
- 冷建立 main logical reservation、participant configuration，不啟 native。
- CollectAsync pin、ServiceWrapperV107 tuple、`IWrapperLifetimeV100.CloseAsync(force)` 與建立失敗的 cleanup retry owner。

唯一業務接線差別：

```fsharp
// 設計片段：service sink 是既有 authoritative 路由，observer 僅通知。
let observeEdge edge =
    serviceSink edge
    notifyEdge sid edge

let connectOutput hub =
    pinPrinter(node, ctx, hub, fun batch -> notifyNative sid batch)
```

兩個 notify 只能 enqueue 到 bounded printer／projection actor，不在 native event callback 同步讀 SQL 或寫 LINE。observer exception 必須記錄並隔離，不讓它阻止 serviceSink／AgentEnd／journal；不可因此丟掉 authoritative event。需要補投影時由 SQL 再讀。raw I/O 可由既有合併／批次策略處理 backpressure；模型完成事件不可當 raw I/O 丟棄。

### 3.4 Service.StartOnNode 的 ownership 與啟動次序

從 V110 搬必要 composition，**不執行它的 run**。流程：

1. 外層用既有 `FodexFunctions.pinBase<ServiceOnNodeInputV100, Task<Result<IActorRef * IAsyncDisposable,exn>>> "1.0.0" target` 取得 bootstrap 函數：這會自動 first-use initialize，不手動 register。此 bootstrap 從 BaseCD pin，與現有 Console.Run／Service.Run 的入口模式相同；不能先碰尚未配置 SQL 的 node partition。收到已建立並完成必要 RN cluster readiness 的 node 後，驗證並安裝 SQL/cache/artifact 設定，與 node 既有值衝突時失敗。其餘函數才走 node registry／DB fallback。
2. 沿現有 Loop factory 4.0.5 建 shared cache、SharedCacheMcp 1.0.0 啟固定 endpoint，驗 health；AGY cache 設定沿已驗證流程。這裡不 Start native、不讀 AGENTS 生成。
3. `make : ServiceCreateV107` pin 新 `Service.CreateObservedWrapper=1.0.0`，所有 live 資源都是 function input／執行期變數，不捕獲進 quotation。
4. pin `ServiceSupervisor=1.0.7` 建 `/user/fodex-supervisor`，保留傳入 `json=true` 供 Provider primitive protocol 解碼；Console 是否顯示 JSON 是另一個 frontend 選項。
5. 返回 `(supervisorRef, disposal)`。不用 wait node.Terminated；外層 v4 host 才擁有整個 lifetime。
6. disposal 依 V110 的次序關 supervisor／wrappers、cache HTTP、cache loop；**不 Terminate 傳入 node**。部分建立失敗亦按已建立資源逆序清理，cleanup failure 不假成功。

原 `Service.Run=1.0.10` 不改成呼叫新 target，避免讓 v4 開發順帶改已驗證 service 預設。待 v4 完整驗證後是否去重，屬另一次 review；本輪不以 DRY 為由同時改所有 host。

### 3.5 Console.RunFrontend 的控制與顯示

保留現有 Console editor 4.0.5／printer 4.0.3／output formatter 4.0.5／readSubmission 4.0.3 的多行、貼上、prompt 重畫邏輯；不再實作一套 ReadKey／ReadLine。console 薄介面只做：讀提交、處理本地 labels/json/exit、交 submit、顯示 ack／非同步輸出。

`submit` 由 v4 host 綁到 Focus/Provider control composition：

- 普通文字及 `/wrapper_*`、`/subagent`、`/model` 等，使用目前 root 的 service bridge，由 IAgent.Request 處理。
- `**` root registry 控制使用 Provider 的共用 domain operation；不給 native 當一般 prompt。
- `/line_context` 在 host 操作 focus。
- `/exit` 取消 outer lifetime，不能只 dispose 當前 wrapper 而留下其他 root。

Console 本身不持有固定 wrapper/factory，不從 graph 直接 Tell native actor。`/show(N)`、`/trace`、`/cancel`、start/stop/remove 範圍以及 ALL/range/list 語法沿既有 wrapper；N 在該 ReActLoop 範圍解讀，跨 wrapper 顯示時必須附 WSID，不能把兩個 root 的 N=2 當同一個 participant。

預設 main raw I/O show、sub 不 show 的既有政策保留。raw `notifyNative` 與 `notifyEdge` 分開格式化，所有背景顯示經同 editor writeBlock/printer 避免破壞正在輸入的多行文字。`/trace` 用 ctx/NLog／actor ILoggingAdapter；child actor 以自己的 logger 建 UniContext，不沿用 parent logger identity。

`--json` 時，stdout 僅正式 JSONL；prompt、啟動狀態、raw I/O 走 diagnostics/stderr。既有 ReActEvent serializer/schema 原樣使用，不外包一層而破壞舊 consumer。LINE 輸入顯示是 host notification（有 source/account/conversation/SID/operationId），不可冒充第二筆 HumanInit 寫入 graph；JSON 顯示用明確 `kind="input_observed"` 的獨立 notification，文件說明如何與既有 ReActEvent schema 分辨，既有 event JSON string 保持原樣。

### 3.6 Quotation、版本與 ROP：不能退回直接呼叫 module

依目前專案模式：

```fsharp
[<AutoOpen>]
module ExampleFodexFunV100 =
    let version = System.Version(1, 0, 0)
    let target = "Example.Operation"

    // Input 送入吃 Input 的函數；保留使用者指定的兩階段語意。
    let quotation : Expr<Input -> FeasibleT<Input, Output, exn>> =
        <@ fun _ -> fun input -> implementation input @>

    [<AutoOpen>]
    module Definitions =
        let builtins = [| FodexFunRegistry.declare target version quotation |]

// 呼叫側：版本在此 scope 首次 resolve 時 pin，後續透過 FeasibleFun.invoke。
let operation =
    FodexFunBinding.pin<Input, Task<Result<Output, exn>>>
        node (Some "1.0.0") target
let! result = FodexFunBinding.invokeAsync operation input
```

片段是 pattern，具體同步/非同步型別須與 3.2 的宣告相符：外層 `FeasibleT` 的同步 Error 與 Task 內 Error 均須保留，不把 Task 包成 Ok 就當成功。測試必須先 eval quotation 再執行 invoke；只測 implementation helper 不算符合要求。

- 新 Definitions.builtins 列入 `FodexFunctions.fsx` 既有 first-use 初始化；使用者／Program 不手動 register。
- AutoOpen 不等於 assembly load 就會執行 module do；沿既有首次求值模式，不重新爭論或新增 startup hack。
- BaseCD 宣告不捕獲 ActorSystem／logger／SqlConnection；node partition 的 Versioned 管理與 function input 的 node 是兩回事。
- SQL quotation fallback／Register 寫回等現有規範保留。不新增 bypass CD mutation、side cache 或靜態 instance dictionary。
- 已編譯舊版繼續 pin 舊版；新 host 使用表列新 target 1.0.0，舊 Service.Run 不受 max version 改動影響。
- 新檔不用 private/internal/RequireQualifiedAccess。詳細 XML 註解寫 what/why/how，尤其 borrowed node disposal 與兩種 output observer。
