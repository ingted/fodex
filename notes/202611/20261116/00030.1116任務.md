## 0. 摘要與已確認決策

本輪要完成三件產品行為：

1. `**dropagent <sid|topic> [--force]`：普通關閉與強制關閉都由 Fodex 管理資源；LINE 不必知道 native 是 AGY 或 Codex。force 可處理缺少舊 provider metadata 的 root，不能繞過預設保護、範圍限制及資源退出驗證。
2. `**whoami` 與 `**listagent` 清楚顯示 `[目前選取]`、`[預設]`。使用者不再靠回看上一則 setagent 回覆，猜普通 prompt／`/next` 的目標。
3. LINE 同一對話持有多個獨立 main wrapper；增加 `**setdefault <sid|topic>`，沒有 root 時自動補一個預設 root。直接執行 Fodex CLI 仍只有該次入口自己的 main wrapper。

已獲使用者明確確認：

- `**setdefault` **只改預設，保留目前選取**；沒有有效選取時才使用預設。
- force 語法固定為 `**dropagent <sid|topic> --force`；不加為 false。
- **即使 force，預設 root 也不能 drop。** 必須先把預設切到另一個 root。
- `**newagent` 建立獨立 root，不自動改目前選取或預設。
- provider type 不明不該使「終止既有資源」變成不能執行；資源封裝由 Fodex 負責。

兩個重要區別：

- **停止／移除 wrapper** 與 **刪除歷史 SQL 資料** 分開。一般 drop 保留原歷史和冪等 receipt、使 root 退出可用清單；使用者只對本輪特定舊 main 明確授權了實體刪除。`--force` 不自動等於 purge history。
- **查不到 provider** 與 **無法證明某程序屬於此 wrapper** 分開。前者不得阻擋 force；後者不能靠猜測或殺全部 codex／agy 補救。未確認退出就回失敗，不回假成功。

## 2. 使用者可見的完整語意

### 2.1 身分與範圍

- 一個 LINE conversation（群組或一對一）就是一個 root namespace；Topic 在這個 namespace 內唯一。
- 對外 `sid` 一律指 **wrapper SID / WSID**。不是 AGY conversation ID、Codex thread ID、actor path 或 process PID。
- 每個 root wrapper 可含 main native 與自己的 sub participants。`**newagent` 不是在目前 root 底下建立 subagent。
- LINE namespace 的 `Topic -> WSID` 保存在現有 SQL，記憶體只作 cache；不可另做 `.json` 或 Dictionary 當第二份 authority。
- 每個非空可用 namespace 恰有一個預設 root，最多一個目前選取；兩者可以相同或不同。
- `main` 是 Topic 名稱，不是特權判定。保護依 default 指向的 immutable key／WSID，不依字串 `main`。
- 已保留的唯一 SID prefix 規則繼續沿用；同對話內唯一才接受，ambiguous prefix 拒絕，不跨對話搜尋。

### 2.2 指令

| 指令 | 行為／是否改選取 |
|---|---|
| `**newagent agy|codex <Topic>` | 新 root、新 WSID；完成 create 後 Ready；不改選取／預設 |
| `**setagent <sid|topic>` | 將目前選取改為指定可用 root；不改預設 |
| `**setdefault <sid|topic>` | 只改預設；指定 root 必須 Ready 且未進入 drop barrier |
| `**whoami` | deterministic 查詢目前實際目標與預設，不呼叫模型 |
| `**listagent` | 列本對話 root；標示目前實際選取與預設 |
| `**[sid 或 Topic] prompt` | 只指定這一筆；不改選取／預設 |
| 普通文字／圖片 | B 時固定有效選取；缺少有效選取才 fallback default |
| `/next` | B 時固定同一個有效選取；領該 root 的結果，以及既有 conversation query/rejection 結果規則 |
| `**dropagent <sid|topic>` | 普通移除；先正常停止所有所屬資源，成功才完成 SQL tombstone |
| `**dropagent <sid|topic> --force` | 強制結束已確認屬於該 root 的資源；不要求知道 provider；仍不可 drop default |

force 是 Argu 的 boolean switch，不新增手刻位置參數 parser。接受 quoted Topic。`--force` 只對 drop 合法；`**newagent agy --force`、多餘 boolean 值／拼錯 switch 必須簡短拒絕。

解析層將目前混在一起的 Argu input 與語意結果分清：Argu input DU 保留各現有 case，新增無參數的 Force；normalize 後回語意 DU 的 `Dropagent of target:string * force:bool`，其餘現有 case 語意不變。別直接把 raw Argu 的 Dropagent 改成兩個必填位置參數，否則「不加 force」會被誤判缺參數。檢查恰有一個主命令、Force 只伴隨 Dropagent；兩個 DU 足夠，不建立多層 parser 類別。

若尚不能普通關閉 MigrationAmbiguous，普通 drop 明確回「舊資料缺少啟動資訊，請使用 `**dropagent <目標> --force` 清理」，不能只把內部 Lifecycle 值丟給使用者。

### 2.3 顯示範例

```text
**whoami
目前選取：test1116
SID：d710324c-98d1-4c07-a145-40c780bae0cc
預設：POC1114AGY
預設 SID：5cb79437-354d-4118-a57c-a985a24485cb
普通訊息與 /next 的目標：test1116
```

```text
**listagent
[目前選取] Topic=test1116 SID=d710324c-... status=Ready
[預設] Topic=POC1114AGY SID=5cb79437-... status=Ready
Topic=POC1114Codex SID=83ef32b4-... status=Ready
```

同一個 root 同時擔任兩者時，同列 `[目前選取][預設]`；實際回覆用完整 SID，以上省略僅為文件排版。MigrationAmbiguous 可列出並提示可 force 清理，但不能被標為有效選取或預設。

`/next` 無結果的訊息必須包含目標，例如 `Topic=test1116 SID=... 目前沒有可領取的結果。`，避免再次誤解查的是整個對話所有 root。這次不另發明 `/next ALL` 或自動跨 root 領取。

`Ready` 表示可恢復的邏輯 root，不保證 OS process 正在跑；不得將 SQL Ready、service list 有無 live bridge、native running 三者混成一個狀態。

### 2.4 空字典與既有資料升級

初始化按 conversation 執行，不在 Provider 啟動時建立一個所有 LINE 對話共用的 root。

1. 第一個該 conversation 的合法請求進 B 時，依同一 transaction／admission lock 確保 default metadata。
2. 若沒有任何可用或已保留的預設 root，reserve 一個預設 root，provider 使用正式設定 `MainAgentType`（目前預設 AGY），完整 argv 保存；通常 Topic=`main`。
3. 舊 MigrationAmbiguous 已占用 `main` 時，保留它、取第一個可用 `main-2`、`main-3`…；命名選擇與 reserve 必須在同一交易，不修改舊 row 偽裝成新 root。
4. 自動補預設在 B **只建立 SQL reservation**，Lifecycle=Provisioning。首次真正使用該 root 的現有 Batch 工作再走 create、RootReady、生成；whoami/list 可以先顯示 Provisioning。不能從 B 呼叫 service，也不新增沒有 durable work 的背景 create。沒有使用者 prompt 就不啟 native、不消耗模型 token。
5. 遷移已有資料時，default 缺少：優先沿用有效目前選取，再選 Ready 的 Topic main，再按 CreatedSequence／KeyHash 選第一個 Ready；都沒有才 reserve 新 root。這個選擇只做一次並保存，不每次重新挑最新 root。
6. 已有有效選取保留；沒有有效選取則有效目標為 default。default 尚在 Provisioning 時不可偷偷換另一個 root，待它 ready；建立失敗回明確錯誤並沿同一 reservation 修復。
7. 若首個請求就是 newagent，仍先確保 namespace 的預設，再建立使用者指定 root。結果可以是兩個 root，但 native 都維持 lazy。自動 default 的候選名稱也要避開這筆明確 newagent 要求的 Topic；例如第一筆要求 Topic=main，default 取 main-2，明確新建 main 仍成功。不能搶先自動占用使用者要建立的名字。

建立 ID 注意：`ReserveRootInTransactionAsync` 以 CreatedRouteId 去重，**不可把同一個 RN RequestRoute 同時傳給自動 default 與 newagent**。自動 default 使用固定演算法衍生的 reservation ID：UTF-8 `line-default-reservation-v1\0<conversation>\0<origin-id-N>` 的 SHA256 前 16 bytes 建 Guid；明確 newagent 仍用原 RequestRoute。這是內部 reservation ID，不冒稱 RN route、不能拿它投遞 LINE。相同 B 重試得到同 ID；不同並行請求由同一 admission lock／default row 阻止重複建立。沿既有 hash helper 實作並固定測試向量。

上述是邏輯字典初始化，不等於把每個歷史 participant eager resume。Provider 重啟不應批次啟動所有 AGY／Codex。

## 3. SQL 與 admission 一致性設計

### 3.1 復用現有 selection 表

不用另建一份 root catalog。既有 `LineFodexV3Sessions` 繼續保存 root；`LineFodexV3Selections` 擴充：

```text
ConversationHash    PK，既有
SessionKey          目前選取，既有
DefaultSessionKey   預設 root，新增 nullable char(64) 作相容 migration
Revision            新增 bigint NOT NULL DEFAULT 0
```

SessionKey 不改欄名，以免所有 Legacy consumer 被迫同時重寫。DefaultSessionKey 在舊 row 初次讀取時補齊；缺整個 row 時連同預設建立。禁止用目前 static 設定覆寫已有 default。

Store 提供少數共用 operation，避免 admission、query、Legacy 各寫一份 fallback：

- `EnsureConversationRootsInTransactionAsync`：上節唯一初始化／遷移流程，回目前 roots、default 與有效選取。
- `SetDefaultInTransactionAsync`：同 conversation、WSID／generation、Ready、無 Drop barrier 全部核對；只寫 DefaultSessionKey 與 Revision。
- `SelectInTransactionAsync`：保留既有 selected 語意，增加 Revision；不覆寫 DefaultSessionKey。
- `ResolveConversationTargetInTransactionAsync`：普通 prompt、圖片、Next、whoami/list 共用的有效目標決策。

可以用一個小 tuple 或單一必要 record 回傳資訊；不要新增多層 repository／runtime／application 類別。仍用現有 AsyncStore、交易 helper 與 SQL applock。

### 3.2 指令順序與快照

- `setagent`、`setdefault`、default protection、force flag、target WSID／generation 在 **B 同一交易** 固定。
- `whoami/listagent` 的 root／選取／預設快照也在 B 取，保存為 Immediate 或等價可重讀結果，不能排到 worker 後才讀到後一個 setagent 的狀態。
- 長 catalog／模型查詢仍維持既有 Query lane；不要為簡單 SQL 查詢跑模型或同步等待 native。
- `**[test1116]` 後若使用者切成另一個 root，先前 batch 仍屬 test1116；不得重新讀 selection 改路由。
- `/next` 固定的是 B 當下有效 root；新的選取不回頭改已 admission 的 carrier。
- setdefault 與 drop 競爭由相同 admission transaction 解決：先 setdefault 就拒絕 drop；先進 Dropping 就拒絕 setdefault。不能 native 已開始關閉後才在 C 發現它變成 default。
- Drop 成功時若被刪的是目前選取，將 SessionKey 改為仍有效的 DefaultSessionKey；**不能整筆 DELETE selections 而連 default 一起丟失**。
- 僅「目前選取」受影響才 fallback；刪非選取 root 不改選取。

### 3.3 冪等與失敗

- Root mapping generation、B receipt、work epoch、C、D 的既有防重規則保留。
- 同一 Origin 重送同一 drop request 只觀察／回原結果；不能改 force 或 target 後沿用同一 request ID。
- C 完成才把 root 設為 Dropped 並清活資源 ownership；close 未確認時維持 Dropping＋可觀察的失敗資訊，不能先從清單移除來掩蓋 orphan。
- 正常 drop 的 SQL history／request receipts 保留；之後相同 Topic 新建，必須得到新 WSID。晚到舊 close 不能殺新 root。
- 不直接 UPDATE 正式 admission／carrier 狀態讓紅測變綠，也不換 request ID 盲目重送 native。

## 4. Fodex.Supervisor 應承擔的功能

### 4.1 清楚的責任邊界

| Fodex.Supervisor | LINE Provider v3 |
|---|---|
| 建立／恢復同 WSID 的 wrapper、IAgent、ReActLoop | 對話 namespace、Topic 別名、目前選取／預設 |
| main/sub native、wrapper/raw 的生命週期 | LINE 指令解析與帳號／對話權限 |
| 所屬 process／Job／actor／hub 的結束與證據 | 將目標與 force 固定在 B，呼叫 service |
| close request 冪等、incarnation fencing | close 成功後 C 的 root tombstone／選取 fallback |
| 原生 SID mapping／graph／operation journal 恢復 | RN 結果領取及 LINE delivery outcome |

不要把 conversation-specific default 再複製進 Fodex service，形成兩份 authority；也不要把程序管理、provider 判斷或 taskkill 寫進 v3。

### 4.2 `IAgent.Stop` 和 Drop 的關係

`IAgent.Stop()` 目前的 Contract 是 `TIAgentStop = Feasible<int,exn>`。沿用它，不為這次直接擴 Contract。

- `Stop` 應停止該 IAgent 負責的執行與所屬 native 資源；對 wrapper，須包括 main 及由它管理的 sub，包含 wrapper/raw、AGY/Codex。
- caller 不提供 provider；實作持有實際 native IAgent、Proc Supervisor handle、Job ownership，這些才是停止依據。
- `Stop` 不刪 logical identity／歷史，以便既有 Start／resume 語意成立。
- Drop 另外完成 root factory 的 hub、bridge、manager、output subscription 等釋放，最後退出 service 活清單與 LINE 可用清單。因此單獨 `Stop` 不等於 purge SQL。
- 所有 public member 繼續走 FeasibleFun／FodexFun registry。不要在 CLI／LINE 直接呼叫 `NativeAgyVxxx.stop` 或對 native ActorRef 自行 Tell。
- Actor mailbox 內不得同步等待自己／同 dispatcher 的 actor 完成 Stop。現行 `WrapperAgentV410` StopAgent 迴圈裡的同步 `native.Stop()` 是此次必須具體檢查、重現並改善的路徑。

### 4.3 普通與 force close 的唯一 service 路徑

沿既有 `op="close"`，以現有 request `text` 欄位承載可選 JSON options：

```json
{"force":true}
```

空 text 或省略 options 等於 false；strict parse，只接受已定義欄位與 boolean。保留舊 wire，不為它開另一個 LINE 私用 endpoint。

service close 的流程：

1. 由指定 WSID 找當前 root resource owner；固定 incarnation、close request ID、force canonical value，journal claim。
2. 暫停新的派工／取消控制等待，由已持有的 IAgent／ReActLoop 操作正常停止。
3. 普通 close 走既有有界正常釋放。force 額外允許在正常 actor 停止失敗／逾時時，從 **root resource owner 已持有的 ownership handle** 強制終止所屬 process／Job，等所有確認退出，再拆其 actor/hub。
4. 沒有 live wrapper 時不能為 close 呼叫 create／resume。只查該 SID 的持久化 operation 與可核實的 ownership；已有完成 receipt 回原 receipt；可證明資源已無的 incarnation 可完成關閉。
5. 所有已知 owned resources 都退出才保存 Completed，並回 nativeCleanupConfirmed；有任一 OS 拒絕／remote 無法確認／未知 ownership 就明列尚未確認的項目，不得回 cleanupCompleted=true。
6. actor restart／new incarnation 後，舊 receipt 不可證明新資源已清除；保留 V106 已修的 generation／incarnation 防護。

**force 的意思是無視 provider metadata、可升級物理停止；不是無視 ownership，也不是 force 刪資料後假裝 process 沒了。** 已有 Proc SDK `StopProc(force=true)` 與 owned Job API，先復用，不另造 process manager。

實作 interface 建議固定如下：保留 FodexAgent 的 object expression，在實作專案宣告一個小型 `IWrapperLifetimeV100`，提供 `CloseAsync(force:bool)`，由同一 factory 持有的資源執行。`IAsyncDisposable.DisposeAsync()` 委派 `CloseAsync false`。這個 interface 不搬進 Contract，不公開裸 Process，不另開全域 mutable registry。

`ServiceWrapperV107` 在既有 `ServiceWrapperV105` 的資料之外，只附加該 factory 已綁定的 `bool -> Task` close operation；service close 不知道 native provider。正常與強制路徑共用同一個 ownership／停止狀態，不各維護一組 children。

避免遞迴：wrapper 的 Stop handler 只執行 participant 停止；factory 的 Close 先等待該 Stop，再釋放 factory resources。不可讓 Stop 回呼 factory.Close、而 factory.Close 又呼叫同一 Stop。force 升級只在 factory 的 resource owner 處串接；不能把它塞進正在等待自己的 actor mailbox。

若 native actor 已死，root owner 仍須握有其未完成 cleanup 的資源引用；不能只有 actor PostStop 才知道 handle。Force 不等待那個已死 mailbox。參考現有 `NativeProcessFodexFunV303` 的 StopPending／failed-start cleanup 保留方式。

已確認的具體 gap：AGY V305、exec V305、app-server V305 都在 actor behavior 內建立 `NativeProcessBindingV303.bind node`；pending resource 只存在該 binding 的本機 CD，root factory 沒拿到可直接收尾的能力。因此本輪確定新增 NativeProcess V304 與三種 native V306，**不是等實作時才決定要不要做**。

接法固定為 root factory 持有一個本機的 owned-resource collection，收錄的是同一 native scope 的 cleanup capability，並非第二份程序權威；不要新增全域 registry。經既有本機 creation configuration 傳入型別化的 registration callback（固定 literal key，值不序列化），wrapper main 與 ParticipantManager 建立 raw/native 時都傳入。nested wrapper 登記的是其 factory CloseAsync，保留其自己的 scope。

每個 native actor incarnation 在任何 Start 前登記自己的 binding；key 包含 logical participant、generation、actor incarnation GUID。Stop 成功且確無 pending launch 才解除登記；actor restart 不可覆蓋舊 incarnation 尚未清完的 scope。root 正在 close 時拒絕新登記／派工。新 binding 對 Start-in-flight 與 force 必須序列化：若 Start 晚完成，將回傳 resource 收尾後才能讓 close 成功，不能先取空 snapshot 就宣告退出。既有 Proc 3.0.3 start/stop quotation 與 NuGet 1.572.17 可沿用，V304 補的是外層 lifecycle／ownership 可達性與競爭控制。

exec 的原生 compact 會暫啟 app-server，也必須走同一個已登記 scope；不能只追一般生成的 process。遠端 participant 的 scope 留在真正持有資源的 node，wire 只傳既有 participant／WSID／generation 與 force；不序列化本機 callback／Job handle。remote 未回退出確認時回 unconfirmed，不能在本機用同名 process 代殺。

### 4.4 Close journal 相容性

`ServiceRequestStoreFodexFunV100` 現有 `ReserveServiceClose of incarnation` 沒有 force payload；新版必須把 canonical force 納入 request fingerprint／Text，避免同 ID false→true 被當成相同操作。

沿現有 `FodexServiceOperationV1.Payload` JSON 記錄擴充，缺 force 的舊 close 視為 false；不得改壞其他 send/receive/control 的 payload。新版 command/type 放新版本檔，保留 V100。

逾時只終止等待，不代表底下 Stop 已取消。重試沿原 operation；要把普通 close 改成 force，使用新的明確 close request ID，不能篡改原 request 的 force。兩者仍受同 root incarnation／resource gate 序列化。

### 4.5 普通 CLI 與 service 同步受益

- CLI 入口仍建立一個 root；`/exit` 使用同一正常停止核心。
- service 可以持有多個 root；close 某 root 不關 service、其他 root、共用 cache server 或 RN/GW。
- MCP service 的 close tool 也要接受同一 optional force，透過同一 service operation；不得另寫 MCP kill 邏輯。
- LINE 的 `--force` 經 transport 呼叫此 API，除此之外不含任何程序終止程式碼。

## 6. 重啟恢復的正確流程與驗證缺口

### 6.1 只重啟 Provider

SQL roots／selection／default 不變；worker換 owner，取得同一 root applock 後接手。Fodex 還活的 wrapper 直接沿原 WSID 使用；新的 Provider RunId／OrderedOwner 不是 wrapper SID。

### 6.2 PTC 與 Fodex service 都重啟

1. SQL authority 不清空；同 conversation 的 Topic、WSID、default、selected 原樣載入。
2. service live bridge cache 初始可以為空，這不能用來判斷 root 已刪除。
3. 下一次需要使用 root 時，`create` 使用已保存的 WSID／argv；建立 IAgent／ReActLoop，還原 graph/session/configuration。
4. native 應在首次需要生成時恢復既有原生 session；provider 未改變且 SID 可用時沿原生 SID。不要把 wrapper WSID 當 native SID。
5. 明確的 type switch／restart-with-handover 才走既定跨 provider 新 native SID 流程；本次不得用「重啟」偷換全新模型對話。
6. 已 DispatchStarted 的工作只 Observe 原 operation；不能把服務重啟當成重新 Send 的授權。需要使用者裁決的 uncertain 工作要清楚呈現。

前輪只有 Provider restart 保留原 live native 的真實證據；**整套停掉再恢復兩個 root 並以 SID 使用，仍必須實測**。不要再把預期行為寫成已驗通過。
